**Windows에서 사용량 한도가 풀리면 똑같은 그 Codex 작업을 자동으로 이어 갑니다.**

Codex가 작업 도중에 멈추고 오전 6시 34분에 다시 해 보라고 말합니다. 오전 6시 34분에 사용자는
자고 있고, 아침에 보면 작업은 멈춘 그 자리 그대로입니다.

Codex Auto Resume은 Codex가 알려 주는 사용량 한도(예를 들어 5시간 한도나 주간 한도)의 재설정
시각까지 기다렸다가, 이어 가도 정말 안전한지 확인한 뒤 **바로 그 대화**를 이어서 진행시킵니다.
돌아왔을 때 멈춰 있는 작업이 아니라 끝난 작업을 보게 됩니다. 일시적인 요청 제한, 네트워크 장애,
시간 초과, 서버 오류, 끊긴 스트림도 복구하지만, 이름을 댈 수 있고 다시 시도해도 안전한 장애일 때만
그렇게 합니다.

Windows ChatGPT/Codex 데스크톱 앱을 위한 작은 로컬 워처입니다. Codex의 로컬 상태를 읽기 전용으로 관찰하고, 무엇이 실패했는지 분류한 뒤,
공식 `codex queue` 명령으로 이어서 하기 메시지 한 건을 보냅니다. 워처 자체에는 네트워크 코드가 없고, 이 프로젝트로 전송되는 것도
없습니다. 재개하기 전의 사용량 확인은 공식 Codex 바이너리에 묻는 것이고 그 답은 OpenAI가 줍니다. 재개된 턴은 직접 시작한 턴과 똑같이 데스크톱 앱 안에서
사용자의 Codex 설정대로 실행되어 OpenAI로 갑니다. Codex 대화 안에서 이 플러그인의 도구와 명령이 돌려준 결과는 그 대화와 함께 OpenAI로 갑니다.
Codex에서 설치할 때는 GitHub에서 릴리스를 내려받습니다. 그리고 v0.5.7로 설치하면 Codex가 사용자가 설정해 둔 모든 Git
마켓플레이스도 새로 고칩니다(이 마켓플레이스만 지정하는 동작은 v0.6.0부터입니다).

**모든 실패를 재시도하지는 않습니다.** 이름 붙일 수 없는 실패는 건드리지 않습니다.

## 설치

**Windows 10/11. Python 불필요. 관리자 권한 불필요.**

### 설치 마법사로 설치 (권장)

[최신 릴리스](https://github.com/songyb111-gachon/codex-auto-resume-windows/releases/latest)에서
`CodexAutoResume-Setup-vX.Y.Z.exe`를 받아(v0.6.10과 그 전의 릴리스에는 없습니다) 더블클릭합니다. 설치는 그것으로
끝이며, 압축을 풀 필요가 없습니다.

<img src="images/install-motion-ko.png" alt="설치 창이 Codex Auto Resume을 설치하는 모습. 창 자신의 그리기 코드가 그렸습니다. 환영 페이지에서 다음, 설치하기 전에 고르는 것, 설치를 누르면 막대가 차오르며 설치 단계가 차례로 바뀌고, 워처가 실행 중이고 대시보드 열기가 켜진 완료 페이지" width="450">

설치 마법사는 [릴리스 압축 파일로 설치](#릴리스-압축-파일로-설치)의 릴리스 압축 파일을 파일 하나에 담은
것입니다. 그 압축 파일을 바이트 그대로, 압축 파일의 SHA-256과 함께 담고 있습니다. 실행하면 압축 파일을 그
다이제스트와 대조해 다르면 멈추고, 임시 폴더 안에 새로 만든 자기만의 폴더에 압축을 푼 뒤, 그곳에서 그 압축
파일의 `Install.cmd`를 실행합니다. 같은 설치 프로그램입니다. 그다음 그 폴더를 지웁니다. v0.6.16부터 이 모든
일을 대시보드와 같은 모양(설치본이 있으면 그 설치본에 설정된 테마)의 자기 창에서, Windows 언어로(다른 언어를 고를
수도 있습니다) 합니다. 무엇을 어느 판,
어느 버전으로 어디에 설치하는지 알려 주고, 설치 프로그램에 실제로 선택지가 있는 것만 묻습니다. 처음 설치할 때 Windows
로그인 시 실행할지, 다른 판이 설치돼 있으면 판을 바꿀지입니다. 설치 프로그램이 얼마나 진행됐고 어느 단계인지 보여
주고, 끝나면 완료됐는지를 설치 프로그램의 종료 코드와 로그와 함께 알려 주며 대시보드를 열지 묻습니다. 같은 버전이
이미 설치된 곳에서 실행하면 먼저 복구와 제거를 보여 줍니다. 복구는 그 자리에 다시 설치하며 설정, 기다리는 모든
작업, 로그인 시 실행 선택을 그대로 둡니다. 제거는 설정과 복구 기록까지 지울지 묻는 제거로 이어집니다. 더 새로운
버전이면 전처럼 업데이트하고, `-Silent`는 어느 쪽도 묻지 않습니다. 콘솔 창은
열리지 않습니다. 대시보드가 열려 있는 설치본을 업데이트할 때는 워처를 다시 시작할 때 그 대시보드에 닫아 달라고
요청하고, 새 버전으로 있던 자리에 다시 엽니다. v0.6.16 이전 버전의 대시보드는 요청을 받지 못하므로 사람이 창을
닫듯이 닫고, 새 버전으로 처음 열렸던 페이지(없으면 개요)에 다시 엽니다. 저장하지 않은 설정 변경이 있는 대시보드는
그 변경을 지키며 열린 채로 남고, 다시 열 때까지 이전 버전으로 실행됩니다. 설치 프로그램은 그런 창에 대해서만 저장하지 않은
변경이 있다고 말합니다. `-Silent`로 할 때도 같습니다. 아무것도 내려받지 않고, 관리자 권한이 필요 없으며, 자체 Python도
가져오지 않습니다. 설치본은 압축 파일 안의 Python으로 실행됩니다. DLL은 Windows의 System32 폴더에서만
불러오므로 다운로드 폴더에서 옆에 놓인 DLL은 절대 불러오지 않으며, 옆에 `.config` 파일이 있으면
멈춥니다. 명령줄에서 실행하면 `-SkipStartup` 같은 스위치를 `Install.cmd`에 그대로 넘기며, 스위치와 평범한
단어가 아닌 것은 거절합니다.

v0.6.16부터 `-Silent`를 붙이면 아무것도 묻지 않고 키 입력도 기다리지 않고 설치합니다.
`CodexAutoResume-Setup-vX.Y.Z.exe -Silent`이며, `winget`이 이 설치 마법사를 이렇게 실행합니다. 그 밖에는 달라지는
것이 없습니다. 출력도 종료 코드도 스위치가 없을 때와 같습니다(0은 완료, 1은 중단, 14는 다른 판이 설치돼 있어
아무것도 바꾸지 않고 끝난 경우로, 물어볼 사람이 없기 때문입니다). 두 번 클릭할 때 콘솔 창이 열리지 않도록 콘솔
프로그램이 아니라 Windows 프로그램으로 만들어졌는데, PowerShell은 시작하기만 한 Windows 프로그램을 기다리지 않습니다.
PowerShell에서는 설치 마법사가 있는 폴더에서 `cmd /c .\CodexAutoResume-Setup-vX.Y.Z.exe -Silent`로 실행하세요. 끝날 때까지 기다리고, 출력을
보여 주고, 종료 코드를 `$LASTEXITCODE`에 남깁니다. `winget`, `.cmd` 스크립트, `cmd /c`는 그대로 기다립니다. 같은
스위치를 압축 파일의 `Install.cmd`와 `Uninstall.cmd`에도 쓸 수 있고, 설치 마법사는 멈출 때 Enter를 기다리지 않습니다.

v0.6.16부터 설치본은 Windows 설정의 앱 목록과 `winget list`에도 *Codex Auto Resume*(고급판은 *Codex Auto Resume
Advanced*)로 나타납니다. 내 Windows 사용자 계정에만 해당합니다. 목록의 제거 버튼은 설치 프로그램이
`%USERPROFILE%\.codex-auto-resume\uninstall\`에 보관해 둔 제거 프로그램을 같은 설치 창에서 실행하며,
`Uninstall.cmd`와 같은 것입니다. 설정과 복구 기록도 지울지 묻고, 제거가 진행되는 모습을 보여 줍니다.
`winget uninstall`은 같은 제거 프로그램을 `-Silent`로, 창 없이 실행합니다. 판을 바꾸면 항목이 다른 판의 것으로 바뀌고, 업데이트하면 다시 쓰입니다.
`CODEX_AUTO_RESUME_PLUGIN_HOME`으로 다른 곳에 둔 설치본에는 보관된 제거 프로그램도 항목도 없습니다.

코드 서명이 없으므로([릴리스 압축 파일로 설치](#릴리스-압축-파일로-설치)의 끝 참조), 실행할 때
SmartScreen이 *Windows의 PC 보호*(Windows protected your PC) 창을 띄울 수 있습니다. **추가 정보**를 누른 뒤
**실행**을 누릅니다. 이 경고는 파일에 서명이 없고 Microsoft에서 아직 평판이 쌓이지 않았다는 뜻일 뿐, 이
프로젝트가 공개한 그 파일인지는 알려 주지 않습니다. 그것은 옆에 공개된 `.sha256`과 attestation이 알려
줍니다. 내려받은 폴더에서 PowerShell로 다음을 실행합니다.

```powershell
(Get-FileHash .\CodexAutoResume-Setup-vX.Y.Z.exe -Algorithm SHA256).Hash
gh attestation verify .\CodexAutoResume-Setup-vX.Y.Z.exe `
    --repo songyb111-gachon/codex-auto-resume-windows `
    --signer-workflow songyb111-gachon/codex-auto-resume-windows/.github/workflows/release.yml `
    --source-ref refs/tags/vX.Y.Z
```

첫 값이 `.sha256` 파일의 값과 같아야 합니다. `scripts/release.json`은 설치 마법사가 아니라 압축 파일의
다이제스트를 고정합니다. 설치 마법사가 담은 압축 파일이 바로 그 고정된 압축 파일이며, 그것까지 확인하는
방법은 [`docs/VERIFY.ko.md`](VERIFY.ko.md)에 있습니다. 설치 마법사가 스스로 하는 다이제스트 확인은 손상된
다운로드를 잡아낼 뿐, 바꿔치기된 파일은 잡아내지 못합니다. 안의 압축 파일을 바꿀 수 있는 사람이라면 옆의
다이제스트도 바꿀 수 있기 때문입니다. Smart App Control을 켜 두었다면 설치 마법사가 **실행** 선택지 없이
차단될 수 있으며, 다른 경로가 실행하는 서명 없는 파일도 마찬가지로 차단될 수 있습니다. 이 프로젝트는
Smart App Control을 끄라고 요청하지 않습니다.

### Codex에서 설치

플러그인을 추가한 뒤, Codex에게 **자동 재개 설정해 줘**라고 말하면 됩니다.

```
codex plugin marketplace add songyb111-gachon/codex-auto-resume-windows
codex plugin add codex-auto-resume@codex-auto-resume-windows
```

그러면 플러그인의 설치 스크립트가 실행됩니다. 이 저장소의 릴리스에서 해당 버전 압축 파일을
HTTPS로 내려받아, 플러그인의
[`scripts/release.json`](https://github.com/songyb111-gachon/codex-auto-resume-windows/blob/main/scripts/release.json)에
그 버전용으로 기록된 다이제스트와 SHA-256을 대조합니다. 이 다이제스트는 릴리스가 공개된 뒤 이 저장소에
커밋되는 것으로, 릴리스 자체에서 오는 값이 아닙니다. 플러그인에 들어 있는 `release.json`에
다이제스트가 없는 버전이면 릴리스에 함께 공개된 `.sha256`과 대조하고, 그렇게 했다고 알려 줍니다.
다이제스트가 기록된 마지막 버전보다 새로운 버전이 여기에 해당하고, 설치된 플러그인 자신의 버전은
언제나 여기에 해당합니다. 릴리스는 자기 자신의 다이제스트를 담을 수 없고, 설치한 뒤에는 플러그인이 설치된
사본에서 실행되기 때문입니다. 이어서 내용이 정말 이 제품의 이 버전인지 확인한 다음에야, 현재
Windows 사용자에게만 설치합니다. 설치되는 것은 설치 폴더(기본값 `%USERPROFILE%\.codex-auto-resume`)
안의 파일, 시작 메뉴 항목(알림이 켜져 있을 때이며, 기본값은 켜짐입니다), 사용자 단위 레지스트리 값, 그리고 Codex에 등록되는 이 플러그인과 그
마켓플레이스(그 설치본을 가리킵니다)입니다. 플러그인의 지침에 따라 Codex가 실행하기 전에 무엇을
할지 먼저 알려 줍니다.

이 경로는 공개된 압축 파일을 내려받으며, v0.5.0부터 v0.5.7까지의 압축 파일은 모두 예전의 단일 작업(single-job) 릴리스
워크플로가 빌드했습니다. 이 워크플로는 GitHub Actions를 고정되지 않은 태그로 참조했고, 그 실행 파일은 바이트 단위로 똑같이 다시 빌드할 수 없습니다. 무엇이
이를 대신하는지는 [릴리스 압축 파일로 설치](#릴리스-압축-파일로-설치)의 2단계에 있습니다. 그 변경은 v0.6.0부터입니다.

GitHub에서 추가한 플러그인에는 스킬과 그 설치 스크립트와 엔진의 Python 소스가 들어 있지만, 그
소스를 실행할 인터프리터가 없고, 매니페스트에는 MCP 서버가 선언되어 있지 않습니다(릴리스가 더하는
`.mcp.json`이 가리키는 실행 파일은 릴리스에만 있습니다). 실제로 실행되는 워처와 설정 창과 패널의
서버와 Windows 런타임은 모두 그 릴리스에서 옵니다.
그래서 다운로드가 필요하며, 스크립트가 무엇을 하고 무엇을 하지 않는지 미리 확인하고 싶다면
[`docs/PLUGIN.ko.md`](PLUGIN.ko.md)를
읽어 보세요.

### 릴리스 압축 파일로 설치

플러그인의 설치 스크립트에 맡기지 않고 릴리스를 직접 내려받고 싶다면:

1. [최신 릴리스](https://github.com/songyb111-gachon/codex-auto-resume-windows/releases/latest)에서
   `CodexAutoResume-vX.Y.Z-win-x64.zip`을 받습니다.
2. **압축을 풀기 전에 확인합니다.** `Install.cmd`는 자신이 들어 있던 압축 파일을 검증하지
   않으므로(해시도 서명도 확인하지 않습니다), 이 단계가 곧 검증입니다. 내려받은 폴더에서
   PowerShell로 다음을 실행합니다.

   ```powershell
   (Get-FileHash .\CodexAutoResume-vX.Y.Z-win-x64.zip -Algorithm SHA256).Hash
   ```

   출력된 값이 압축 파일 옆에 공개된 `.sha256` 파일의 값, 그리고 `main` 브랜치의
   [`scripts/release.json`](https://github.com/songyb111-gachon/codex-auto-resume-windows/blob/main/scripts/release.json)에
   그 버전용으로 기록된 다이제스트와 같아야 합니다 (`Get-FileHash`는 대문자로 출력하지만 대소문자는
   상관없습니다). `.sha256`은 압축 파일과 같은 곳에서 오므로 파일이 온전하다는 것을 보여 줍니다.
   `release.json`의 값은 릴리스 파일이 아니라 이 저장소의 커밋이므로 별도의 기록이며, 이 값을
   바꾸려면 `main`에 새 커밋이 필요합니다. 이 값은 릴리스가 공개된 뒤에 추가되므로
   막 나온 버전은 아직 없을 수 있고 v0.5.1까지의 버전은 항목이 없으며, 아래의 attestation 확인은 이 값과 무관하게 할 수 있습니다.
   GitHub CLI가 있다면 어느 워크플로 실행과 어느 커밋이 이 파일을 빌드했는지 확인할 수 있습니다
   (attestation은 v0.5.4 이후의 압축 파일에 있습니다).

   ```powershell
   gh attestation verify .\CodexAutoResume-vX.Y.Z-win-x64.zip `
       --repo songyb111-gachon/codex-auto-resume-windows `
       --signer-workflow songyb111-gachon/codex-auto-resume-windows/.github/workflows/release.yml `
       --source-ref refs/tags/vX.Y.Z
   ```

   하나라도 맞지 않으면 파일을 지우고 실행하지 마세요. 각 확인이 무엇을 증명하고 무엇은 증명하지 못하는지는
   [`docs/VERIFY.ko.md`](VERIFY.ko.md)에
   있습니다. v0.5.0부터 v0.5.7까지의 압축 파일은 모두 예전의 단일 작업(single-job) 릴리스 워크플로가 빌드했습니다. 이
   워크플로는 GitHub Actions를 고정되지 않은 태그로 참조했고, 그 실행 파일은 바이트 단위로 똑같이 다시 빌드할 수 없습니다. 빌드와 공개 작업의 분리,
   정확한 커밋에 고정한 action, 재현 가능한 실행 파일은 공개된 v0.6.0 릴리스에 포함됩니다.
3. 아무 곳에나 압축을 풀고 **`Install.cmd`**를 더블클릭합니다.

압축 파일이 자체 Python 런타임을 담고 있어서 미리 설치할 것이 없고, 끝나면 권장 설정이 이미 켜져 있습니다. `Install.cmd`는 스스로 아무것도 내려받지
않습니다. Codex 플러그인도 압축 파일 안의 파일로 등록하므로 이 경로에서도 패널까지 함께 설치됩니다. 다만 Codex에 마켓플레이스 새로 고침은 요청합니다. v0.5.7과 그 이전 설치 프로그램은 모든 Git 마켓플레이스의 새로 고침을 요청합니다. v0.6.0부터의 설치 프로그램은 이 제품의 마켓플레이스만 지정하므로, 방금 등록한 로컬 마켓플레이스에
대해서는 아무 일도 일어나지 않습니다. Codex가 무언가를 가져오는 것은 예전에 GitHub에서 등록한 이 마켓플레이스가 재지정 뒤에도 남아 있을 때뿐입니다.

이 프로젝트가 빌드하는 것은 어느 것도 Authenticode 서명이 되어 있지 않습니다. 두 실행 파일도, 설치
마법사도, `Install.cmd`와 `Uninstall.cmd`도, PowerShell과 Python 스크립트도 마찬가지입니다. 함께 들어 있는
Python 인터프리터(`pythonw.exe`, `python.exe`와 Python DLL이며, 인터프리터의 Visual C++ 런타임
DLL 두 개는 Microsoft가 서명했습니다)는 Python Software Foundation의 서명을 그대로 유지하며,
워처는 그 `pythonw.exe`로 실행됩니다. 설치 마법사 경로에서 SmartScreen이 묻는 것은 설치 마법사
하나뿐입니다. 설치 마법사가 푼 파일에는 내려받은 파일 표시가 없으므로, 그 안의 `Install.cmd`는 다시
묻지 않습니다. 어느 경로로 설치하든 Smart App Control을 켜 두었다면
서명되지 않은 두 실행 파일, 곧 설정 창 `CodexAutoResumeSettings.exe`와 Codex가 플러그인의 도구와
패널을 위해 실행하는 `codex-auto-resume-mcp.exe`가 차단될 수 있습니다. 이 수동 경로에서는
탐색기가 내려받은 파일 표시를 유지하므로 `Install.cmd`와 `Uninstall.cmd`도 차단될 수 있고, 게시자를
알 수 없다는 SmartScreen 경고가 뜰 수 있습니다. 이런 경고나 차단은 파일에 서명이 없고 Microsoft에서
아직 평판이 쌓이지 않았다는(또는 인터넷에서 내려받은 스크립트 형식이라는) 뜻일 뿐, 이 프로젝트가
공개한 그 파일인지는 알려 주지 않습니다. 그것은 2단계가 알려 줍니다.

### 어느 쪽이든

어느 경로든 같은 설치본 한 곳(기본값 `%USERPROFILE%\.codex-auto-resume`)에 설치됩니다. 워처 하나,
데이터베이스 하나, 설정 파일 하나, 로그인 항목 하나입니다. 어느 것이든 다시 실행하면 업그레이드이자
복구 경로이며, 대기 중인 재개를 그대로 유지합니다. 업그레이드할 때는 새 버전이 이어받도록 실행 중인
워처에 멈춰 달라고 요청하고 최대 1분까지 기다립니다. 강제로 종료하지는 않으며, 이전 워처가 아직
하던 일을 마치는 중이면 그대로 두고 그렇다고 알려 줍니다. 이 플러그인의 MCP 런처가 파일을 열고
있어서 Codex가 플러그인을 교체하지 못하면, 설치 프로그램은 그 런처를 강제로 종료하고 다시 시도합니다.
Codex는 다음에 필요할 때 새 런처를 시작합니다. 그래도 교체하지 못하면 설치 프로그램은 그렇다고 알리고 나머지를
모두 마칩니다. 플러그인의 도구는 이미 방금 설치한 프로그램으로 실행되며, Codex가 따로 가진 플러그인 사본의
스킬 글만 ChatGPT/Codex 앱을 닫고 설치 프로그램을 다시 실행할 때까지 기다립니다. v0.6.11부터 설치본의
판이 바뀐 경우에는 그 사본이 아직 어느 판인지 설치 프로그램이 알려 주고, 사본이 바뀔 때까지 대시보드의 진단도
그렇다고 알려 줍니다. `Uninstall.cmd`를 실행하거나 Codex에게 제거를
요청하면 제거됩니다. 경로마다 무엇이 남는지는 [제거](#제거)를 참고하세요.

대시보드 진단 페이지의 **업데이트 확인**은 GitHub에 더 새로운 릴리스가 공개되었는지 묻고 설치를
제안합니다. v0.6.16부터 설치는 설치 마법사와 같은 창에서 진행됩니다(확인하는 설치본이 v0.6.16 이상일 때입니다. 그보다
이전 버전은 늘 하던 대로 업데이트합니다).
내려받은 파일을 확인한 뒤 어느 버전에서 어느 버전으로 바뀌는지와 그 버전의 새로운 점을 그 파일에서 읽어 보여 주고,
**업데이트**를 눌러야 설치합니다(**나중에**는 아무것도 설치하지 않습니다). 그다음 진행 정도와 로그를 보여 주고, 새로운
점의 첫 몇 줄과 함께 업데이트되었다고 알려 줍니다. 그 전에 실행되던 것은 모두 새 버전으로 저절로 다시 실행됩니다.
워처는(멈춰 두었고 로그인 시 실행도 꺼져 있었다면 그대로 둡니다) 알림 영역 아이콘과 함께, 이 대시보드는 새 버전으로
다시 열립니다. `-Silent`로 하는 업데이트도 워처를 같은 방식으로 다시 시작하고, 창은 열지 않습니다. v0.6.11부터는 더 새로운 *사전 릴리스*도 찾습니다. 사전 릴리스는 릴리스가 마무리되기 전에
공개된 `-alpha` 또는 `-beta` 빌드로, 릴리스보다 덜 테스트되었습니다. 지금 쓰는 버전과 최신 릴리스보다
모두 새로운 것이 있고 먼저 제안할 릴리스가 없으면 설치할지 묻는데, Enter가 누르는 단추는 **나중에**입니다.
예라고 하면 옆에 공개된 체크섬과 대조한 뒤 그 사전 릴리스를 지금 쓰는 판 그대로 지금 버전 위에 설치하며,
설정과 일시 정지, 대기 중인 항목, 로그인 시 실행 선택은 모두 그대로 둡니다. 그 밖에는 아무것도 사전
릴리스를 설치하지 않습니다. 워처도, Codex 안의 패널도, Codex의 도구도 설치하지 않으며,
`scripts/bootstrap.ps1 -Update`는 여전히 릴리스만 설치합니다. 명령줄에서는 `-CheckOnly`가 찾은 사전
릴리스를 따로 한 줄(`prerelease: v<버전>`)로 출력하고, `-Version <버전>`이 그것을 설치합니다. GitHub의
목록을 읽지 못하면, 사전 릴리스에 기대지 않는 릴리스에 대한 답과 함께 사전 릴리스는 확인하지 못했다고 알려 줍니다.
GitHub가 한 네트워크에 허용하는 요청 수(한 시간에 60번이며, VPN이나 공유 연결에서는 그 연결을 쓰는 모두가 함께
씁니다)가 바닥나 거절했다면 그렇다고, 그리고 한도가 언제 재설정되는지 알려 주며, **다른 버전 설치...**도 같은
내용을 알려 줍니다. 명령줄에는 `releases: rate-limited <재설정 시각>` 또는 `releases: unread`가 출력됩니다.

설치 후에는 **시작 메뉴 → Codex Auto Resume**에서, 또는 Codex에게 *자동 재개 설정 열어 줘*라고
말해서 설정을 바꿀 수 있습니다.

**설정 > 앱에 없거나 로그인 시 시작되지 않나요?** Codex 앱과 Claude 데스크톱은 자신이 시작하는 모든 프로그램에
레지스트리와 `%APPDATA%`의 비공개 보기를 따로 주며, Windows 자체는 그것을 읽지 않습니다. 그 안에서 실행한 설치나
업데이트 - 에이전트가 실행한 설치 마법사나 `Install.cmd`, 또는 Codex가 시작한 워처의 아이콘에서 연 대시보드 -
는 설정 > 앱의 항목, 로그인 시 실행, 알림의 이름, 링크 처리기, 시작 메뉴 항목을 Windows가 보지 않는 곳에 남길 수
있었습니다. v0.6.17부터 설치 마법사, `Install.cmd`, 업데이트 스크립트 자체의 복구 단계, 대시보드는 이를 알아차리고 스스로 그 앱
밖에서 다시 실행되며, 밖으로 나가지 못한 대시보드는 복구, 업데이트 설치, **다른 버전 설치...**, **Windows 로그인 시 실행**
변경을 하지 않고 그 이유를 말합니다. 그 판단은 창이 무엇에서 시작되었는지에 따른 것이라 틀릴 수 있으니(역시 패키지 앱인
Windows Terminal 탭에서도 그렇게 판단될 수 있습니다), 시작 메뉴에서 대시보드를 열어 거기서 하세요. 그래도 이렇게 되었다면 시작 메뉴에서
대시보드를 열고 - 시작 메뉴에 항목이 없으면 파일 탐색기에서 `%USERPROFILE%\.codex-auto-resume`의
`CodexAutoResumeSettings.exe`를 열고 - 진단 페이지에서 **설치 복구**를 누르세요.

### 다른 버전 설치

대시보드 진단 페이지의 도구 카드 맨 끝에 있는 **다른 버전 설치...**는 고른 버전을 고른 판으로, 지금 버전
대신 설치합니다. 더 새 버전이든 오래된 버전이든, 표준판이든 고급판이든 됩니다. 두 판을 나란히 둘 수는 없으므로
(Codex 홈 하나에 워처 하나, 플러그인 하나, 로그인 항목 하나), 언제나 그 창이 속한 설치본을 바꿉니다.
Codex에는 아무것도 보내지 않으며, 다른 곳에서는 이 기능을 제공하지 않습니다. 워처도, Codex 안의 패널도,
Codex의 도구도 제공하지 않습니다.

누르면 그때 비로소 GitHub에 이 저장소의 릴리스 목록 전체를 30개씩 최대 다섯 쪽까지 묻습니다. v0.6.2부터의
모든 버전을 공개된 판마다 최신 버전부터 보여 주며, 고급판은 v0.6.11-alpha부터 있습니다. 설치할 수 없는 버전도
목록에 흐리게 남아 그 까닭을 말합니다. 지금 쓰는 버전이거나, 그 번호로 그 판의 압축 파일이 공개되지 않았거나,
대조할 체크섬이 없거나, 설치 프로그램이 판보다 먼저 나와서 판을 먼저 바꿔야 하거나, 관리자의 정책이 있는데 그
버전은 그것을 지키지 않는 경우입니다([아래](#관리자가-정하는-설정)). GitHub에 물을
수 없거나 답을 읽을 수 없으면 그렇다고 말하고 아무것도 보여 주지 않습니다. v0.6.2보다 이전 버전은 제공하지
않습니다. v0.6.0과 v0.6.1에서는 대시보드가 내려받은 파일을 확인할 수 없고, v0.5의 설치 프로그램은 일시 정지한
복구를 일시 정지된 채로 두지 않아서, 그 버전에서는 대시보드로 다시 돌아올 수 없기 때문입니다.

**사전 릴리스도.** 사전 릴리스도 릴리스처럼, 오래된 것도 새로운 것도 두 판 모두에서 제공합니다. 이름으로
골라 확인한 사전 릴리스는 릴리스처럼 설치하며, 오래된 것은 필요하면 상태를 먼저 바꿉니다. *업데이트 확인*은
여전히 지금 쓰는 버전과 최신 릴리스보다 모두 새로운 가장 최근 사전 릴리스만 제안하고, 다른 것은 이 목록에서
고릅니다.

행을 고르고 **설치...**를 누르면 먼저 묻고, Enter와 Esc가 누르는 단추는 **나중에**입니다. 질문은 해당하는 것만
말합니다. 사전 릴리스라서 릴리스보다 덜 테스트되었다는 것, 오래된 버전이라서 그 뒤에 나온 것은 들어 있지 않고 그
버전이 모르는 설정이나 값은 그곳에서 기본값으로 읽혀 다음에 설정을 저장할 때 사라진다는 것, 상태를 먼저 그
버전에 맞게 바꾼다는 것(아래), 표준판으로 바꾸면 고급 기능과 그 코드가 사라지고 고급판으로 바꾸면 고급 기능이
모두 꺼진 채 시작한다는 것, v0.6.11-beta.2보다 이전의 고급판은 이 버전의 고급 설정을 읽을 수 없어서 그곳에서는
고급 기능이 모두 꺼지고 설정은 나중 버전을 위해 남겨 둔다는 것, 그리고 무엇이든 실행하기 전에 내려받은 파일을
고정된 다이제스트나 공개된 체크섬과 대조한다는 것입니다.

예라고 하면 목록을 다시 읽고(보여 줄 때처럼 제공되지 않게 된 버전은 아무것도 설치하지 않습니다), 그 버전의
압축 파일(고정된 다이제스트가 없으면 그 `.sha256`도)을 내려받아 모든 설치가 하듯 파일과 내용을 확인한 뒤에야
설치 잠금을 잡습니다. 더 오래된 상태를 읽는 버전, 곧 v0.6.11-beta부터 v0.6.14까지와 v0.6.15 핫픽스(스키마 4)나 v0.6.2부터 v0.6.11-alpha까지(스키마 3)는
이어서 워처에게 멈추라고 요청하고 최대 1분 기다리며 절대 강제로 끝내지 않고, `downgrade-state --to 4`나 `--to 3`이
하듯 상태를 바꿉니다. 지금 상태의 사본을 옆에 남기고, 이미 Codex로 갔을 수 있는 이어서 하기 메시지는 끝난 것으로 해서 다시
보내지 않으며, 사용자를 기다리던 대화와 Codex가 아직 이어서 하기 메시지를 전달할 수 있는 대화는 끄고, 지켜보기만이 켜져
있으면 일시 정지로 바꿉니다. 1분 안에 멈추지 않는 워처가 있으면 아무것도 설치하지 않고 상태도 그대로 두지만,
그 워처는 멈추라는 요청을 받았으므로 그 뒤에 멈출 수 있고, 그때 다시 시작해 주는 것은 없습니다. 머리글이 워처가
돌지 않는다고 말하면 **워처 시작**을 누르세요. 바꾸기에 실패하면 워처를 다시 시작하고 아무것도 설치하지 않습니다. 그다음 그 버전 자신의 설치 프로그램이 설치 창에서 돌며(다른 버전을 설치한다는 머리글 아래, 막대는 내려받기와 단계로 차오르고, 끝나면 종료 코드와 로그를 보여 줍니다) 모든 기록, 일시 정지, 로그인 시
실행 선택을 그대로 둡니다. v0.6.16보다 오래된 버전은 설정 > 앱의 항목도, 그것을 위해 보관한 제거 프로그램도 모르므로, 그 둘이 있는 설치본
위에 그런 버전을 고르면 먼저 둘을 지웁니다. 이 모든 것이 도는 동안 페이지의 모든 동작 단추는 **워처 시작**까지 흐리게 표시됩니다.

설치되었고 *대시보드 열기*가 선택되어 있으면 새 대시보드가 열리고 이 창은 업데이트 뒤처럼 닫힙니다. 그렇지 않으면 창은 워처가 이제 설치한 버전으로 도는지, 그리고 상태를 바꿨다면 이어서 하기 메시지 몇 개를 끝난 것으로 했고 대화
몇 개를 껐는지 말합니다. 설치한 버전으로 돌게 하려면 창을 닫았다가 다시 여세요. 쓰고 있는 판의 오래된 버전이면
확인 창은 그 버전에서 *업데이트 확인*으로 돌아오라고도 말하지만, 그것이 될 때만 말합니다. 릴리스에서라면 어느
버전의 확인이든 최신 릴리스를 권하고, 사전 릴리스에서라면 확인이 사전 릴리스를 권하는 첫 버전인 v0.6.11-beta.2
이후의 버전만 그렇게 하며, 어떤 확인도 판을 바꾸지 않습니다. 그 밖에는 이 버전의 릴리스 페이지에서 그 설치
마법사로 돌아오세요. 상태를 바꾼 뒤 설치 프로그램이 실패하면 상태는 바뀐 채로 남으며(덜 보낼 뿐 더 보내지는
않습니다), 창은 무엇이 남는지 말하고, 바꾸기 전 상태의 사본은 상태 폴더에 남아 있습니다.

시작 메뉴에서는 대시보드가 열립니다. Codex를 꺼 둔 상태에서도 동작하는 독립 창으로, 워처가 무엇을
하고 있는지, 무엇이 대기 중이고 언제 다시 확인하는지, 무엇이 어떻게 끝났는지, 최근 일주일 수치, 워처
상태, 그리고 설정을 한 창에서 보여 줍니다. 머리글의 불빛은 워처가 하는 일을 보여 줍니다. 워처가 실행 중이고 자동 복구가
켜져 있으면 불빛은 청록색이고 알림 영역 아이콘처럼 깜빡입니다. 감시 중에는 점이 천천히 흐려졌다가
돌아오고, 다 켜진 뒤에 작은 빛이 번졌다가 거두어집니다. 기다리는 중에도 감시 중과 똑같이 숨 쉬고, 때가 된
작업을 확인할 때는 작은 호가 돌고, 복구 중에는 조금 더 빠르게 깜빡입니다. 일시 정지되었거나 멈추면
빛나지 않는 회색이고, 확인이 필요하면 주황색으로 그동안 내내 천천히 깜빡입니다. 옆의 단어가 늘 어느
상태인지 알려 줍니다.
설정 > 모양의 **테마**는 창, 팝업, 알림 카드를 밝게 또는 어둡게 그리며, 기본값인 *시스템 설정
따르기*는 Windows에 설정된 앱 모드를 따릅니다. 그 옆의 **Codex 안의 테마**는 패널만의 설정입니다.
*테마와 같게*(기본값이며, 이 설정이 생기기 전의 모든 패널이 그랬습니다), *Codex 테마 따르기*, *밝게*,
*어둡게* 가운데 고르므로, 창은 밝게나 어둡게로 두고 패널은 Codex를 따르게 할 수도, Codex가 어떻든 패널을
한 테마로 둘 수도 있습니다.
화면 언어나 테마가 바뀌면(창에서 저장했든, Codex에서 바꿨든,
Windows가 밝게와 어둡게 사이에서 바뀌었든) 창이 스스로 닫혔다가 같은 페이지, 같은 자리에서 다시
열립니다. 다만 저장하지 않은 변경 사항이 있을 때는 다시 열지 않습니다. 같은 모양 부분의 **움직임
줄이기**는 이 애니메이션을 멈추며, Windows 자체의 애니메이션 설정도 항상 따릅니다. 고대비 모드에서는
테마와 상관없이 그림자와 색조를 뺍니다. 네이티브 창이며, 로컬 웹 서버를 띄우거나 브라우저를 여는
일은 없습니다.

v0.6.10부터 모양 부분에 있는 **디자인**은 대시보드, 팝업, 알림 카드, Codex 안의 패널을 세 가지
가운데 하나로 그립니다. 밝게 또는 어둡게는 여전히 테마가 정합니다. 기본값인 *부드럽게*는 위에서 말한
대로 입체감이 있습니다. *클래식 (v0.6.2)*은 v0.6.2처럼 평평합니다. 가는 선과 왼쪽 가장자리의
가는 강조 막대가 있는 흰 카드이고, 지금의 탭에는 밑줄이 그어지며, 불빛은 빛과 함께 숨 쉽니다.
*단순하게*는 모서리가 작은 평평한 회색 모양이고, 불빛은 빛 없이 흐려집니다. 모든 디자인이 똑같이
움직입니다. 스위치는 미끄러지고 알림 카드는 떠오르며 들어옵니다. 움직임을 멈추는 디자인은 없고, 그 일은
위의 움직임 줄이기가 합니다. 디자인 설정이 처음 생긴 릴리스에 있던 *부드럽게, 움직임 없이*는 부드럽게가
움직임 줄이기 아래에서 그리는 것과 똑같았으므로 이제 움직임 줄이기가 되었고, 그것을 골라 두었던 대시보드는
움직임 줄이기가 켜진 부드럽게로 열려 전과 똑같이 보입니다. 단어와 배치와 크기는 모든 디자인에서 같고, 대기 중과 기록 목록은 어느 디자인에서나 평평한 줄입니다. 고대비는 모든 디자인을
대신하고, 움직임 줄이기는 어느 디자인에서든 움직임을 멈춥니다. 디자인은 대시보드에서만 정합니다.
Codex는 패널을 그것으로 그리지만 바꿀 수는 없고, 권장 설정으로 되돌리면 부드럽게로 돌아갑니다. 밝은
테마에서 디자인별 팝업은 이렇습니다.

대기 중인 복구마다 왜 기다리는지와 언제 다시 확인하는지가 보이고, **기다리는 이유**는 선택한 작업에
대해 워처가 마지막으로 기록한 안전 확인 목록을 보여 줍니다. v0.6.11부터는 목록 아래에, 통과하지 못한
첫 확인이 무엇을 기다리는지(Codex 앱, 대화가 열리기, 사용량 재설정 등)를 말로 적은 문장이 붙습니다. 복구의
**진행 기록**에는 기록 뒤에, 이어서 하기마다 전달에서 드러난 것이 나옵니다. 대화에서 턴을 시작한 것이 확인된
시각, Codex에 넘겼지만 아직 확인되지 않았다는 것, 또는 전달 여부가 불확실해 하루 동안 지켜보고 다시 보내지
않는다는 것입니다. v0.6.11부터 **시도** 열은 작업이 쓴 횟수를 지금 허용되는 횟수 옆에 보여 줍니다.
`3/4`처럼 보이며, 제한을 낮춘 뒤에는 `19/6`처럼 보이고 제한에 맞춰 줄이지 않습니다. 컨텍스트 비용 보호가
켜져 있으면 중단의 종류 옆에 그 대화가 사용한 토큰 수도 나옵니다. 줄마다 있는 **자동 재개** 스위치는
그 작업이 속한 대화의 자동 복구를 끄거나 켭니다. 클릭에는 그 줄을 그릴 때의 정확한 중단과 대화가
함께 실리며, 누르는 사이에 끝났거나 사라졌거나 다른 대화의 것으로 밝혀진 작업에 대한 클릭은 거절되고
아무것도 바꾸지 않습니다. 어느 쪽이든 스위치는 아무것도 보내지 않습니다. **지금 다시 확인**은 워처에게
지금 다시 살펴보라고 요청할 뿐입니다. 모든 확인은 그대로 적용되고, 전부 통과해야만 보냅니다.
**취소**는 그 중단과 그것을 이어받는 것 전부의 복구를 멈춥니다. 아직 보내지 않은 기록은 그대로
취소하고, 이미 Codex에 넘어갔을 수 있는 것은 표시만 해 두었다가 아직 큐에 있으면 되가져오며, 이미
끝난 기록에도 표시를 남겨 그 작업의 이후 실패가 새 연쇄를 시작하지 못하게 합니다. 이미 Codex에서
실행 중인 턴은 멈추지 않으며, 확인 문구가 그렇게 말해 줍니다. **모두 취소**는 대기 중인 복구
전부에 같은 일을 정확한 기록 하나씩 합니다. 한꺼번에 다시 시도하는 기능은 일부러 두지 않았습니다.
v0.6.16부터 모두 취소 다음의 **다시 살펴보고 정리**는 확인을 받은 뒤 기다리는 복구를 모두 워처 자신의
규칙으로 다시 살펴봅니다. 복구를 정리하는 것, 곧 직접 한 작업으로 대체된 것으로 멈추는 것은 증거가 있을
때뿐입니다. Codex 기록에서 그 복구의 바로 그 실패한 턴 뒤에 직접 시작한 턴이 있어야 하고(이 도구의 이어서
하기는 결코 세지 않습니다), 그 기록이 아직 대화 파일을 따라잡지 못했다면 파일 자체에 같은 증거가 있어야
합니다. 파일에서는 되돌리기 뒤의 것은 아무것도 증거가 되지 않습니다. 여전히 그 대화의 마지막 실패인 복구는 그대로 기다리게 두며, 재설정 유예 시간, 미룬 시각, 보류,
스위치, 예산 같은 모든 확인이 그대로 적용됩니다. 워처는 깨어나 때가 된 것을 살펴봅니다. 판단할 수 없는
것은 그대로 두고 판단 못 함으로 세며, 살펴보는 사이에 바뀐 복구는 건너뜁니다. 아무것도 보내지 않고,
Codex에 아무것도 쓰지 않고, 시도 횟수를 되돌려 주지 않고, 아무것도 앞당기지 않으며, 취소되었거나 끝났거나
진행 중인 복구와 기록 페이지는 그대로 둡니다. 버튼 옆 안내는 몇 개를 정리했고, 다시 확인했고, 판단하지
못했고, 그사이 바뀌었는지 말해 주며, 각 복구의 진행 기록에 어느 쪽이었는지 남습니다.
**이 대화는 끄기**는 그 대화에서 대기 중인 복구를 취소하고, 다시 켤 때까지 그 대화의 자동 복구를 꺼
둡니다. 그러면 대기 중 페이지와 기록 페이지에 **이 대화 다시 켜기**가 나타납니다. v0.6.11부터는
각 행에 행만의 메뉴도 있어, 오른쪽 클릭이나 Shift+F10, 메뉴 키로 엽니다. **미루기**는 그 작업을 30분,
1시간, 3시간 뒤나 내일 09:00까지 미루며, 언제나 더 나중으로만 미룹니다. 그 메뉴 맨 아래의 **미루지 않기**는
사용자가 미룬 것을 다시 거둬, 그것이 없을 때 일정이 말하는 시각으로만 되돌립니다. 이의 제기 시간의 시각,
재시도 대기, 사용량 재설정은 모두 그대로이며, 지금 다시 확인은 미룬 시각을 결코 앞당기지 않습니다. **이어 가도록 허용**은
사용자를 기다리는 작업을 한 번 확인한 뒤 이어 가게 합니다. **이 대화를 이어 가는 방식**은
[조용한 시간과 대화를 이어 가는 방식](#조용한-시간과-대화를-이어-가는-방식)에 적은 네 가지 가운데 하나를 그 대화에만 고릅니다.
**이 프로젝트 이어 가기 허용**과 **이 프로젝트 보류**는 그 작업의 대화가 속한 프로젝트에 대해
[지켜보기만, 그리고 어떤 대화와 프로젝트를 이어 갈지](#지켜보기만-그리고-어떤-대화와-프로젝트를-이어-갈지)에 적은 대로 정합니다. 대시보드의
메뉴 맨 끝에만 있는 **이 대화에 쓸 메시지...**는 그 대화에 따로 쓸 이어서 하기 메시지를 정하고, v0.6.16-beta.3부터
그 뒤의 **이번에만 덧붙일 말 추가...**는 그 작업의 다음 이어서 하기 메시지에만 한 번 덧붙일 말을 정합니다. 둘 다
[이어서 하기 메시지](#이어서-하기-메시지)에 적은 대로입니다. 어느
것도 아무것도 보내지 않고, 그 사이 행이 다른 작업이 되었으면 거절되며, 알림 영역 팝업도 작업을
오른쪽 클릭하면 메시지를 뺀 같은 메뉴를 보여 줍니다.

전부 보여 줍니다. 주간 한도를 모두 썼으면 **기다리는 이유**가 그 한도가 재설정되는 날짜와 시각도 알려 주고,
계정에 재설정 크레딧이 있으면 Codex의 `/usage`에서 쓸 수 있다고 덧붙입니다. 크레딧이 있는지는 이 제품이
알지 못합니다. 이미 지난 재설정 시각은 말하지 않습니다. 읽은 것이 그보다 오래되었기 때문입니다. 이를 위해
따로 읽는 것은 없습니다. 사용량은 전과 같이 복구할 때가 되었을 때에만
읽고, 보여 주는 것은 그렇게 읽은 것 가운데 마지막 것이므로 몇 시간 전의 것일 수 있으며, 그만큼 전이라고
적힙니다. 남기는 것은 읽은 시각과 숫자뿐입니다. 어느 창인지, 얼마나 썼는지, 그 길이와 재설정 시각이며,
계정도 요금제도 크레딧도 남기지 않습니다. (고급판의 재설정 동작 두 가지는 규칙이 기다리는 동안 스스로 사용량을
읽고, 그 가운데 하나는 재설정 크레딧이 몇 개인지 보관합니다. 고급판의 사용량 미터를 켜면 고른 간격으로 스스로
사용량을 읽고, 그때부터 이 줄과 아이콘의 툴팁은 그 가장 새로운 값을 보여 주며, 정한 한도 근처에서 알림을

워처가 실행 중인 동안에는 알림 영역에도 아이콘이 나타납니다. 워처 프로세스 자신의 것이라서 워처가
시작하면 생기고 멈추면 사라집니다. 워처 상태는 표시 자체가
말하고 배지는 붙지 않으므로, 대시보드의 작업 표시줄 단추와 같은 그림입니다. 툴팁은 자동 복구가 일시 정지 상태인지, 몇 건이 대기 중이고 몇 건이
Codex에서 실행 중인지, 다음 확인까지 얼마나 남았는지를 보여 주고, 실패한 복구가 있으면 사용자가 볼 때까지
그것을 말합니다.

v0.6.11부터 버전을 보여 주는 모든 곳은 고급판이 설치되어 있으면 그 판도 화면 언어로 함께 보여 줍니다. 대시보드 아래쪽의
버전, 진단 페이지의 버전 행, Codex 안 패널의 머리글이 그렇고, 판은 버전 뒤에 더 작은 회색 글씨로
붙습니다(`v<버전>` *고급판* 같은 모양). 아이콘의 툴팁은 제품 이름 뒤에 판을 붙입니다. v0.6.14부터 표준판은 그 모든
곳에 버전만, 툴팁에는 제품 이름만 보여 주며, 표준판이라는 이름은 판을 서로 가려야 하는 곳에만 나옵니다.
**다른 버전 설치...**처럼 판을 고르는 곳, 그리고 Codex가 아직 다른 판의 플러그인 사본을 가지고 있다고
설치 프로그램과 진단이 알려 주는 곳입니다. 고급판 설치본의 고급판 부분을 불러오지 못하면 표준판으로 실행되며,
그 자리에 *고급판 - 불러오지 못함*이라고 씁니다.

아이콘은 이미 가진 표시 그대로 움직입니다. 워처가 감시하는 동안에는 머리, 곧 고리 끝의 밝은 점이 4.4초마다
아이콘의 짙은 파랑 쪽으로 흐려졌다가 돌아오며 숨 쉬고, 세 번 숨 쉰 뒤에는 가장 밝은 채로 고리의 흰 획을
따라 시계 방향으로 쓸고 갔다가 돌아옵니다. 3.52초 나가고, 끝에서 잠깐 머물고, 3.52초 돌아오고, 1.54초
제자리에 있습니다. 움직이는 동안에는 숨 쉬지 않고, 고리 위쪽의 틈은 결코 건너지 않습니다. 복구가 진행되는
동안에는 숨 쉬지 않고 두 배 빠르게, 3.96초마다 한 번씩 나갔다 돌아오기를 되풀이합니다. 일시 정지되면 회색이고 멈춰 있고, 사람이 봐야 할 일이 생기면 주황색으로 바뀌어 그동안
제자리에서 5.6초마다 천천히 숨 쉬고, 복구가 실패하면 빨간색으로 바뀌어 복구 중처럼 나갔다 돌아오기를
두 배 빠르게, 1.98초마다 한 번씩 되풀이하면서 1.2초마다 깜빡이고, 사용자가 볼 때까지 빨간 채로 있습니다. 아이콘을 클릭해 팝업을
열거나 대시보드를 앞으로 가져오면 돌아오고, 그 뒤에 새 복구가 시작되어도 돌아옵니다. 움직임 줄이기, Windows의 애니메이션 설정, 고대비, 배터리 절약 모드에서, 세션이 잠겨 있는
동안, 그리고 Windows가 아이콘을 아무도 보지 않는 넘침 플라이아웃에 두고 그 플라이아웃이 닫혀 있는 동안에는 움직이지 않으며, 플라이아웃을 열어 둔 동안에는 움직입니다. 대시보드가
열려 있는 동안에는 작업 표시줄 단추도 같은 방식으로 움직이고, 같은 이유로 멈춥니다.

## 먼저 읽어야 할 제한 사항

이 도구는 Windows ChatGPT/Codex 데스크톱 앱이 **현재 로드하고 있는 스레드만** 자동 재개할 수 있습니다.

앱을 재시작하면 대상 스레드는 `notLoaded` 상태가 됩니다. 그리고 **미로드 스레드를 프로그램적으로 깨우는
지원된 방식은 확인되지 않았습니다.** 실측했을 때 미로드 스레드에 큐로 넣은 메시지는 스레드가
미로드 상태로 있던 90초 동안 큐에만 남고 대화 턴으로 전달되지 않았습니다. 증거는
[`docs/evidence/unloaded-thread-delivery.json`](https://github.com/songyb111-gachon/codex-auto-resume-windows/blob/main/docs/evidence/unloaded-thread-delivery.json)에
있습니다. 그런 메시지는 나중에 스레드가 다시 로드될 때 Codex가 전달할 수도 있습니다. 그래서 이
도구는 방금 로드된 것을 확인한 스레드에만 메시지를 큐에 넣고, 메시지가 도착하기 전에 스레드가
미로드로 보고되면 자기가 넣은 메시지를 거둬 달라고 Codex에 요청합니다. Codex가 회수를 확인해 주지
않으면 메시지가 큐에 남을 수 있으며, 그 기록은 `submission_unknown`으로 표시되고 다시 보내지
않습니다.

따라서 미로드 스레드는 **사용자가 ChatGPT 앱에서 그 대화를 직접 열어야만** 이후 자동 재개됩니다.
그전까지 워처는 `waiting_for_loaded_thread` 상태로 조용히 기다립니다. 창과 Codex 패널은 이를
공개 코드 `waiting_thread`로 다루며 화면에는 "대화 열기 대기"로 보여 주고, 명령줄은 상태와
코드를 나란히 출력합니다. 화면 자동화를 쓰지 않고,
대화를 강제로 열지 않으며, 혹시나 하는 마음으로 메시지를 큐에 넣지도 않습니다.

터미널의 Codex TUI나 VS Code 확장 같은 다른 Codex 세션에서 열려 있는 대화는 또 다른 경우입니다. Codex 앱이 쥐고 있지는 않지만
미로드도 아닙니다. 다른 세션이 열어 두고 있기 때문입니다. 이 대화는 그 나름의 이유를 달고 기다립니다. "다른 Codex 세션(터미널 또는
VS Code)에서 열려 있습니다. Codex 앱이 잡으면 이어집니다."라고 보이며, 아무것도 보내지 않습니다. Codex 앱이 그 대화를 쥐게 되면 이어집니다.

즉 **앱 재시작을 넘나드는 완전 무인 자동 재개가 아닙니다.** 이 문서는 그렇지 않은 척하지 않습니다.

## 프로젝트 방향

> 복구 엔진은 작고, 로컬이고, 보수적이고, 실패하면 닫히게(fail-closed) 유지합니다. 복잡함은
> 런타임이 더 많은 일을 하게 만드는 데가 아니라, 설치하고 제어하기 쉽게 만드는 데 씁니다.

복구 엔진은 일부러 작은 워처 하나로 두었습니다. 나머지는 모두 그 워처를 보고 제어하기 위해 있습니다.
독립된 Windows 창(v0.5.7까지는 설정 창, v0.6.0부터는 대시보드), MCP로 연결되는 Codex 안의 설정 패널,
명령줄, 워처 자신의 알림 영역 아이콘과 그 아이콘이 여는 팝업, 그리고 Windows 알림입니다. 이 가운데
어느 것도 혼자서는 아무것도 복구할 수 없고, 워처는 이것들이 열려 있든 없든 계속 실행됩니다.

이 프로젝트가 여전히 두지 않는 것: 별도의 알림 영역 프로세스, 관리용 웹 UI, supervisor 프로세스, Windows
서비스, 두 번째 복구 엔진, 두 번째 상태 데이터베이스. 알림 영역 아이콘과 그 팝업도 예외가 아닙니다.
둘 다 워처의 것이라서 없는 워처를 있는 것처럼 보여 줄 수 없고, 그 메뉴와 버튼과 스위치가 제공하는
모든 것은 다른 화면과 같은 제어 계층을 거칩니다.

**두 판.** v0.6.11부터 제품은 한 저장소에서 같은 버전으로 만들어 내는 두 판으로 나옵니다. **표준판**은 이 안내서가
설명하는 제품입니다. 프로젝트의 기준 - [안전 모델](#안전-모델)과 [개인정보](#개인정보)가 약속하는 것도 그 가운데
있습니다 - 을 하나도 빠짐없이 지키고, 새로 얻는 것도 그 기준을 지킵니다. 더한 것은 모두 사람이 바꾸기 전까지
꺼져 있거나 그 앞 릴리스가 하던 대로 합니다. **고급판**은 표준판에 그 기준 가운데 하나를 일부러 벗어나는 기능을
더한 것입니다. 기능마다 어느 기준을 벗어나는지 밝히고, 그것을 읽은 사람이 켜기 전까지 꺼져 있으며, 사람이 동의한
조건이 더는 맞지 않게 되면 스스로 다시 꺼집니다. 다만 같은 페이지에서 그 자체의 경고를 본 뒤 켜 둔 채로 두기를
고르면 - 그러면 기능도 함께 켜집니다 - 끌 만한 일을 대신 적어 둡니다. 다른 기능이 필요한 기능은 같은 확인 한 번으로, 두 설명을 모두 보여 주며 그
기능도 함께 켜고, 필요한 기능을 끄면 그것을 필요로 하는 기능이 먼저 꺼집니다. v0.6.14부터는 지금 보내기가 켜져 있으면 그 페이지에서 기다리는 복구 하나를 지금 보낼 수도
있고, 고른 사용량 재설정 때 재설정 크레딧을 쓰거나 직접 쓴 메시지를 보내도록 정할 수도 있으며, 저마다 할 일을 할
때까지 대기 중 페이지의 예약됨에 나옵니다. 기능은 대시보드에서, 고급판이 더하는 **고급 기능**
페이지에서만 켭니다. 그 코드는 표준판 압축 파일에서 빠지고, `build/edition_audit.py`가 릴리스를 빌드할 때마다
압축 파일의 바이트를 직접 읽어 그 어느 것도 없음을 증명합니다. 설치본은 같은 판 안에서만 업데이트되고, 다른
판으로 옮기는 것은 재설치입니다. 어느 판에 무엇이 있고 앞으로 무엇이 올지는 [로드맵](ROADMAP.ko.md)에
있습니다. 두 판이 각각 무엇이고 기능 하나하나가 무엇을 하는지는 [EDITIONS.ko.md](EDITIONS.ko.md)에, 모든
기준과 그것이 어떻게 지켜지는지는 id별로 [STANDARDS.ko.md](STANDARDS.ko.md)에 있습니다.

*두 번째 상태 데이터베이스*의 유일한 예외는 고급판의 상태입니다. 어느 기능이 켜져 있는지, 저마다 얼마나 썼는지,
무엇을 했는지, 선택과 규칙이 있는 기능에 사람이 정한 선택과 규칙, 어느 기능이 어느 중단을 맡았는지, 아무것도
분류하지 못한 실패의 표본, 재설정 규칙, 그리고 보낼 때까지는 재설정 때 보낼 메시지의 내용은 워처 자신의 상태와 따로 `config/advanced/advanced.sqlite`에 두므로, 그 때문에 표준판의
데이터베이스가 바뀌는 것은 없습니다(`advanced/tests/test_advanced_state.py`). 이 파일은 고급판에만 있고, 거기서도
무언가를 처음 켜거나 바꿀 때에야 만들어집니다. 표준판은 이 파일을 만들지 않으며, `Uninstall.cmd -Purge`는
`config\`의 나머지와 함께 이것도 지웁니다.

## 기능

- 사용량 한도와, 분명하게 분류된 일시적 장애를 서로 다른 정책으로 복구합니다. 분류하지 못한 장애는
  재시도하지 않습니다.
- 정확한 스레드 UUID를 추적합니다. `--last`를 쓰지 않고, 스레드를 추측하지 않습니다.
- 실제 재설정 시각을 알 수 있으면, 정해진 몇 시간을 자는 대신 그 시각까지 기다립니다.
- 무엇이든 보내기 전에 데스크톱 앱이 실행 중인지, 스레드가 정말 로드되어 있는지 확인합니다.
- 같은 중단을 두 번 재개하지 않습니다. 크래시나 워처 재시작을 겪어도 마찬가지입니다.
- 대기 상태를 재부팅에도 남는 SQLite에 영속적으로 저장합니다.
- 중단된 스레드가 여러 개여도 각각 따로 처리합니다.
- 상한 있는 재시도 대기 늘리기, 전역 중지 스위치, 스레드별 제어를 제공합니다.
- 단일 인스턴스 보호, 선택적인 사용자 단위 Windows 자동 시작, 보수적인 제거를 갖췄습니다.
- 설정을 바꾸는 방법이 세 가지(시작 메뉴의 대시보드, Codex 안의 패널, 명령줄)이고, 모두 같은
  검증기를 거쳐 같은 파일에 쓰므로 서로 어긋날 수 없습니다.
- 화면 언어는 열여섯 개입니다([언어](#언어) 참고). 직접 고르지 않으면 Windows를 따릅니다.
- 밝은 테마와 어두운 테마가 있습니다. 직접 고르지 않으면 대시보드와 팝업은 Windows를, 패널은
  Codex를 따릅니다. 고대비는 언제나 따릅니다.
- 이어서 하기 메시지를 다듬을 수 있습니다. 언어, 간단히·기본·자세히 스타일, 또는 직접 쓴 문장(직접
  입력)을 고를 수 있고, 미리보기는 워처가 보낼 때 쓰는 바로 그 코드로 만듭니다.
- 대시보드는 워처가 무엇을 하는지와 작업마다 왜 기다리는지를 보여 주고, 대기 중인 작업마다 자동
  재개 스위치를 답니다. 알림 영역 아이콘의 팝업은 같은 상태와 다음 확인, 대기 중인 작업 최대 세 개를
  보여 줍니다.
- 전 과정에 걸쳐 Windows 알림을 보냅니다. 중단 감지, 복구 시작, 결과, 그리고 완전히 멈췄을 때입니다.
  알림마다 체크박스가 있고 전체를 켜고 끄는 스위치가 하나 있으며, 중단 알림에서는 그 복구를 취소하거나
  대시보드를 열 수 있습니다.

## 동작 방식

```
사용량 한도 도달
  -> 워처가 Codex의 로컬 기록을 읽기 전용으로 읽고 usageLimitExceeded를 발견
  -> 정확한 스레드 UUID를 자기 SQLite 상태에 기록
  -> 재설정 시각까지 대기
  -> ChatGPT 앱이 실행 중이고 그 스레드가 로드되어 있는지 확인
  -> 실시간 사용량 가용성을 다시 확인
  -> codex queue --thread <UUID> --message "<이어서 하기 메시지>"
  -> 같은 스레드가 원래 작업을 이어서 진행
```

이어서 하기 메시지의 내용은 두 설정이 정합니다. 기본값으로 화면 언어를 따르는 **이어서 하기 언어**와
**메시지 스타일**입니다. 기본값인 *기본*은 작업이 멈춘 이유를 말하고 다시 시도해 달라고 합니다("사용량
초과로 작업이 중단되었습니다. 다시 시도해주세요."). *간단히*는 다시 시도해 달라고만 하고, *자세히*는
기존 대화와 지금의 작업 상태를 확인한 뒤 이미 끝난 일은 되풀이하지 말고 이어 가 달라고도 요청하며,
*직접 입력*은 사용자가 쓴 문장을 보냅니다. v0.6.2까지는 중단 종류마다 고정된 영어 문장 하나였습니다.
워처는 자기가 시작한 턴을 정확히 알아보려고 메시지 뒤에 한 줄을 덧붙입니다. 어떤 스타일도 무엇을
복구할지를 바꾸지 않습니다. [이어서 하기 메시지](#이어서-하기-메시지)를 참고하세요.

로드 상태는 Windows 재시작 관리자(Restart Manager)로 판정합니다. 앱 자신의 `codex.exe` 엔진은
스레드가 로드되어 있는 동안, 정확히 그동안만 그 스레드의 writer lock 파일을 열어 둡니다. 이 도구는
그 소유 정보를 읽기만 하며, 앱의 파일에 잠금을 거는 일은 없습니다.

## 요구 사항

- Windows 10/11.
- 공식 Windows ChatGPT/Codex 데스크톱 앱. 실행 중이어야 하며, 엔진이
  `%LOCALAPPDATA%\OpenAI\Codex\bin\<hash>\codex.exe`에 있어야 합니다.
- 엔진은 자동으로 찾으며, 어떤 버전도 버전 문자열만으로 신뢰하지 않습니다. Codex 업데이트 전이든
  뒤든, 찾은 버전은 `codex queue`가 여전히 `--thread`와 `--message`를 제공할 때만 받아들입니다. 그러면
  `status`와 `doctor`가 그 버전을 세 단어 가운데 하나로 부르며, 셋 모두 똑같이 보냅니다. 그 정확한 버전에서
  실제 복구가 확인했으면 *검증됨*, v0.6.7부터는 제작자 자신의 점검이 그 정확한 버전에서 통과했고
  그 이상 확인된 것이 없으면 *점검됨*, 호환성 데이터가 그 버전에 대해 아무 주장도 하지 않으면
  *호환됨*입니다. 데이터가 점검했거나 검증한 버전에서 로컬 확인이 실패하면 *이 PC에서 실패*로
  읽습니다. 그때는 원인이 그 버전보다 이 PC일 가능성이 높으며, *호환되지 않음*과 똑같이 아무것도
  보내지 않습니다. 그 인터페이스를 증명하지 못하는 것은 추측하지 않고 거부합니다.
- Codex 업데이트는 엔진을 다른 `bin\<hash>` 폴더에서 시작할 수 있습니다. 그러면 워처가 모든 확인을
  포함해 엔진을 다시 찾습니다. 찾아 둔 파일이 없어지거나 바뀌었을 때, 그리고 그 파일은 그대로인데
  앱이 다른 공식 빌드에서 Codex 서버를 실행할 때입니다. 이런 변화마다 곧바로 찾습니다. 그 빌드가
  확인에 실패하면(업데이트가 아직 그 빌드를 쓰는 동안에는 그럴 수 있습니다) 1분 뒤에 다시 시도하고,
  그 뒤로는 간격을 매번 두 배로 늘려 최대 15분마다 시도합니다. 확인할 때마다 시도하지는 않으며,
  빌드가 통과하면 워처를 다시 시작하지 않아도 됩니다.
- 그 확인을 통과하는 빌드가 둘 이상이면(업데이트가 옛 빌드를 새 빌드 옆에 남겨 둘 수 있습니다)
  ChatGPT 앱이 Codex 서버로 실행하고 있는 빌드를 씁니다. 그런 빌드가 정확히 하나가 아니면 아무것도
  고르지 않으며, `--codex-exe`나 `codex_exe` 설정으로 하나를 지정할 때까지 복구는 기다립니다. 그렇게
  지정한 엔진은 언제나 지정한 그대로 씁니다.
- 사용자의 PC도 어떤 버전에 대해 말할 수 있습니다.
  [codex-compat-reporter](https://github.com/songyb111-gachon/codex-compat-reporter)는 따로 있는
  공개 도구로, 이 설치본의 기록을 보고서 하나로 만듭니다. 횟수와 상태와 시각만 담고, 대화 내용도
  식별자도 넣지 않으며, 보내기 전에 사용자가 먼저 읽습니다. 보고서는 사용자가 직접 풀 리퀘스트를 열 때만 GitHub에
  가고, 그 풀 리퀘스트를 어떻게 확인하고 접수하는지는
  [CONTRIBUTING.ko.md](CONTRIBUTING.ko.md#호환성-보고서-보내기)에 있습니다. 제작자의 손 없이 보통 몇 분 안에
  접수하며, 그다음 풀 리퀘스트는 보고서가 어디로 갔는지, 또는 왜 기다리는지 알려 주는 댓글 하나와 함께
  닫힙니다. 다른 사람이 보낸 보고서는 이 프로젝트의 근거와 따로 보관되고, 자기 등급인 *보고됨*을 가집니다.
  보고됨은 그 낱말들 옆에 서고, 어떤 경우에도 그중 하나가 되지 않습니다. 보낸 사람의 컴퓨터에서 손으로
  지어내지 않았다는 것을 증명할 방법이 없기 때문에, 보고는 버전을 사다리 위로 올리지 못하며, 그 버전의
  자체 근거가 아무 말도 하지 않으면 보고가 몇 건 오든 *호환됨*으로 남습니다.

  v0.6.10부터 대시보드의 진단 페이지는 이것을 *Codex 버전* 바로 아래에 흐린 글자 한 줄로 보여 줍니다.
  *다른 사람들의 보고: 성공 3 · 실패 1 · 둘 다 아님 1* 같은 식이며, `doctor`와 `compat`도 같은 횟수를
  출력합니다. 세는 것은 컴퓨터가 아니라 보고서이며, GitHub 이름 하나와 Codex 버전 하나에 보고서
  하나입니다. 보고서가 전달한 기록 가운데 하나라도 복구로 끝났으면 *성공*, 하나라도 실패한 복구로
  끝났으면 *실패*, 전달한 기록 가운데 어느 쪽으로도 끝난 것이 없으면 *둘 다 아님*으로 셉니다. 아무것도
  전달하지 않은 보고서도 *둘 다 아님*입니다. 기록이 두 가지를 다 말하는 보고서는 양쪽에 모두 세며, 그때
  줄 끝에 *양쪽에 모두 셈*과 그 수를 덧붙입니다. 그래서 성공과 실패와 둘 다 아님을 더하고 그 수를 빼면
  보고서 수가 됩니다. 이 저장소에 접수된 보고서만, 그리고 내 버전과 정확히 같은 버전의 것만 셉니다.
  *아직 없음*은 그 버전에 접수된 보고서가 없다는 뜻이고, 버전을 보증할 수 없는 확인일 때는 버전과 마찬가지로
  그 자리에 *-*가 나옵니다. 횟수는 호환성 데이터 옆에 있는 따로 된 파일에 담겨 릴리스와 함께 옵니다. 그것을
  받아 오는 요청은 없으므로, 나중에 접수된 보고서는 다음 릴리스를 기다립니다. 이 횟수는 아무것도 바꾸지
  않습니다. 어떤 기능의 상태도, 어떤 확인도, 워처가 보내는 어떤 것도 이 수를 따라 움직이지 않으며, Codex에는
  이 수를 건네지 않습니다. Codex 패널의 호환성 카드는 그 대신 대시보드를 가리킵니다.

**두 설치 경로 모두 Python이 필요하지 않습니다.** 설치본이 자체 런타임(Python 3.13.15)을 함께
가져오고, 플러그인의 설치 스크립트는 PowerShell입니다. Python 3.12 이상은 소스 체크아웃에서 엔진을
직접 실행할 때만 필요합니다. CI가 돌리는 버전은 [테스트](#테스트)를 참고하세요.

## 무엇을 복구하고 무엇을 복구하지 않는가

자동으로 복구합니다:

| 장애 | 정책 |
| --- | --- |
| 사용량 한도 (`usageLimitExceeded`) | 실제 재설정 시각까지 기다린 뒤 실시간 사용량을 다시 확인 |
| 연결 실패 (`httpConnectionFailed`) | 상한 있는 대기 늘리기 |
| 시간 초과 (HTTP 408/425) | 상한 있는 대기 늘리기 |
| 일시적 요청 제한 (HTTP 429, `rateLimitExceeded`, 그리고 429를 달고 온 `responseTooManyFailedAttempts`) | 상한 있는 대기 늘리기. 첫 대기는 최소 1분 |
| 서버 오류 (HTTP 5xx, `serverOverloaded`, `internalServerError`) | 상한 있는 대기 늘리기 |
| 스트림 중단 (`responseStreamDisconnected`, `responseStreamConnectionFailed`) | 상한 있는 대기 늘리기 |

절대 복구하지 않습니다. 사람이 판단해야 하고, 재시도는 시도 횟수만 낭비합니다:

사용자 취소 · 권한 · 승인 필요 · 콘텐츠 정책 · 잘못된 요청 · 컨텍스트 길이 초과 ·
영구 인증 실패 (401/403, `unauthorized`) · `badRequest` · `sandboxError` ·
상태 코드가 429가 아닌 `responseTooManyFailedAttempts` · **분류되지 않은 모든 것**.

터미널의 TUI나 VS Code 확장 같은 다른 Codex 세션이 쥐고 있는 대화는 복구할 실패가 아닙니다. Codex 앱이 그 대화를 쥘 때까지 그 나름의
이유를 달고 기다리며, 아무것도 보내지 않습니다.

Codex는 턴이 실패하기 전에 실패한 요청을 스스로 몇 번 다시 시도합니다.

대화가 모델의 컨텍스트 창보다 길어서 실패한 턴은 표준판에서 다시 시도하지 않습니다. Codex가 먼저 스스로 압축하고, 그래도 턴이 실패하면 Codex에서
직접 `/compact`를 실행하고 이어 가세요. 이 프로그램은 `/compact`를 보내지 않습니다. 큐에 넣은 "/compact"는 Codex에 평범한 글로 도착합니다.

분류는 구조적으로 합니다. Codex가 기록하는 `codexErrorInfo` variant를 먼저 보고, 그 variant가 담은
HTTP 상태 코드를 봅니다. 메시지 문구는 구조화된 코드가 아예 없을 때만, 그리고 코드가 없는 전송 계층
장애에 한해서 참고합니다. 구조화된 코드를 메시지 문구가 뒤집는 일은 없습니다.

복구에는 세 겹의 상한이 있습니다. 하나의 중단마다 최대 4회, 눈에 보이는 진전 없이 3번 연속 복구되면
멈춤, 그리고 한 작업이 받을 수 있는 이어서 하기는 그 작업의 모든 실패를 통틀어 최대 6회입니다.
복구 턴이 다시 실패하면 새 예산으로 시작하지 않고 같은 연쇄를 이어받습니다. 작업당 상한은 1~10만
받습니다. 사용자가 그 대화를 직접 이어서 진행했다면 오래된 중단은 그 위에 덮어쓰지 않고 버립니다.

## Codex에서 관리하기

설치하고 나면 어느 경로로 설치했든 같은 스킬을 쓸 수 있습니다. 앱에서 이렇게 말하면 됩니다.

> 자동 재개 설정해 줘

그다음부터는 "자동 재개 상태 보여 줘", "대기 중인 자동 재개 보여 줘", "자동 재개 설정 열어 줘",
"자동 재개 꺼 줘"와 "자동 재개 다시 켜 줘", "이 작업 자동 재개 취소해 줘", "자동 재개 통계 보여 줘",
"이 복구 진행 기록 보여 줘", "지금 다시 확인해 줘", "이 복구 시도 횟수 돌려줘", "워처 시작해 줘",
"복구 기록 지워 줘", "자동 재개 메시지 미리 보여 줘", "자동 재개 제거해 줘"처럼 말하면 됩니다.

"자동 재개 메시지 미리 보여 줘"는 플러그인의 도구 20개 가운데 하나인 `preview_recovery_message`를
씁니다. 읽기 전용이라 아무것도 저장하거나 보내지 않고, 중단 종류 하나에 대해 워처가 보낼 문장을 지금의
언어와 스타일로, 또는 미리보기에만 쓸 언어와 스타일로 보여 줍니다. Codex는 화면 언어, 이어서 하기
언어, 메시지 스타일(직접 입력으로 바꾸는 것까지), 테마를 바꿀 수 있지만 직접 입력 문장은 쓸 수 없습니다. 그
문장은 대화에 자동으로 보내지므로 대시보드의 설정 > 이어서 하기 메시지에서만 씁니다. 무엇이 움직일지도 바꿀 수
없습니다. 움직임 줄이기와, v0.6.10부터 있는 디자인도 대시보드에서 정합니다. Codex 안의 패널은 둘 다 따라
그립니다.

자동화를 줄이는 쪽에는 확인을 받으라는 표시가 없습니다. 자동 복구 일시 정지, 대화 하나 끄기, 지금
다시 확인, 복구 미루기가 그렇고, 메시지 미리보기는 읽기 전용입니다. 다시 켜기, 설정 변경, 워처 시작, 복구 취소, 시도 횟수 되돌리기,
사용자를 기다리는 복구를 이어 가도록 허용하기, 기록 지우기는 MCP의 `destructiveHint`로 승인을 요청합니다. 실제 확인 창은 Codex와 승인 설정에 달려 있습니다.
이 프로젝트의 테스트는 도구 어노테이션만 확인하며, 이번 릴리스에서 실제 Codex의 승인 동작을 관찰한 적은 없습니다.

플러그인은 명령줄과 시작 메뉴 창이 쓰는 것과 같은 검증된 제어 계층 위에 놓인 얇은 앞단입니다. 도구는
그 계층을 직접 호출하고, 도구를 쓸 수 없을 때만 스킬이 명령줄로 넘어갑니다. 두 번째 엔진도,
백그라운드 서비스도 추가하지 않습니다. 상태는 플러그인 디렉터리 바깥의
`%USERPROFILE%\.codex-auto-resume\`에 두므로, 플러그인을 업데이트하거나 제거해도 대기 중인 재개를
잃지 않습니다. 워처는 Codex 앱을 닫아도 계속 실행되며, Windows에 로그인할 때 다시 시작됩니다.

플러그인 구조, 설치 스크립트가 무엇을 하고 무엇을 하지 않는지, 업데이트와 제거의 수명 주기, 그리고
사용량 한도 안내에 왜 체크박스를 넣지 않는지는
[docs/PLUGIN.ko.md](PLUGIN.ko.md)에
있습니다.

### 채팅 옆의 패널

Codex 안의 설정 패널은 대화 안뿐 아니라 대화 옆, Codex 앱의 오른쪽 사이드 패널에도 놓일 수 있습니다.

- **채팅 옆에 열기.** Codex가 패널을 그곳에 보여 줄 수 있는 곳에서는 패널 아래쪽 막대가 *채팅 옆에 열기*로 시작합니다. 이
  단추는 Codex에 패널을 오른쪽 사이드 패널로 옮겨 달라고 요청할 뿐 어떤 도구도 부르지 않습니다. Codex가 패널을 대화 안에
  두면 그 페이지에서는 단추가 사라지고 막대가 *Codex가 패널을 이 자리에 두었습니다.*라고 말합니다.
- **사이드 패널의 탭.** 패널의 도구 *Open Auto Resume settings*는 대화의 사이드 패널에 자신을 내놓으며, 플러그인의 도구를
  나열하는 Codex 앱은 새 탭 > 더 많은 도구... 아래에 그것을 보여 줍니다.
- **돌아오면 다시 읽기.** 채팅 옆에서는 사용자가 패널로 돌아올 때 상태를 다시 읽습니다. 15초에 한 번을 넘지 않고, 거기서
  무언가를 바꾸는 중일 때는 절대 읽지 않으며, 키보드는 있던 컨트롤에 그대로 둡니다. 타이머는 돌리지 않습니다.

Codex 앱이 패널을 그곳에 제대로 보여 주는지 재는 측정 MP1~MP3은 `codex-cli 0.162`와 `codex-cli 0.163`에서 통과했습니다
([LIVE_ACCEPTANCE.ko.md](LIVE_ACCEPTANCE.ko.md)).

> 설치본은 하나이며, 두 경로 모두 그 하나로 모입니다. 소스 체크아웃도 함께 돌리신다면 둘 중 하나만
> 남기세요. 상태가 나뉘면 워처가 둘이 되고, 워처가 둘이면 같은 작업을 두 번 재개할 수 있습니다.
> 설치 과정이 이를 감지하고, 두 번째를 만드는 대신 거부합니다.

## 소스에서 실행하기

개발용이거나, 직접 돌려 보고 싶을 때를 위한 방법입니다. 제품을 설치하는 세 번째 방법이 아니라 엔진만
따로 돌리는 것이어서 설정 창도, 패널도, 함께 들어 있는 런타임도 없고, PATH에 **Python 3.12 이상**이
있어야 합니다(CI는 3.12, 3.13, 3.14에서 돌립니다).

```bash
git clone https://github.com/songyb111-gachon/codex-auto-resume-windows.git
```

```bash
cd codex-auto-resume-windows
```

빌드할 것은 없습니다. 먼저 환경을 확인하세요.

```bash
python src/auto_resume.py doctor
```

`doctor`는 메시지를 큐에 넣지 않고 Codex의 파일을 하나도 쓰기 모드로 열지 않습니다. 만들 수 있는 것은
이 도구 자신의 상태 폴더와 로그 폴더, 각 폴더에 두는 소유 표시 파일, 그리고 로그 파일뿐이며, 그것도
없을 때만 만듭니다. 찾아낸 엔진, 앱이 페어링되어 있는지, 재시작 관리자 프로브가 동작하는지, 로컬 기록을
읽을 수 있는지를 알려 줍니다.

## 빠른 시작

```bash
python src/auto_resume.py doctor
```

```bash
python src/auto_resume.py enable
```

```bash
python src/auto_resume.py run
```

`run`은 포그라운드에 머물며 폴링합니다. 작업하는 동안 터미널에 띄워 두세요.

무엇을 하고 있는지 확인하기:

```bash
python src/auto_resume.py status
```

```bash
python src/auto_resume.py pending
```

```bash
python src/auto_resume.py logs
```

멈추기:

```bash
python src/auto_resume.py disable
```

```bash
python src/auto_resume.py stop
```

`disable`은 중지 스위치입니다. 대기 중인 기록은 남긴 채 이후의 재개를 모두 즉시 막습니다. `stop`은
실행 중인 워처 프로세스에 종료를 요청합니다.

## 명령

| 명령 | 하는 일 |
|---|---|
| `doctor` | 아무것도 큐에 넣지 않는 환경 점검: 엔진, 앱 페어링, 재시작 관리자, 기록 |
| `enable [thread-id]` | 자동 재개를 전역으로, 또는 스레드 하나에 대해 켭니다 |
| `disable [thread-id]` | 중지 스위치: 모든 자동 재개를, 또는 스레드 하나만 멈춥니다 |
| `status` | 활성화 여부, 워처 상태, 자동 시작, 엔진, 기록 수 |
| `pending` | 재개를 기다리는 중단 (`--all`, `--json`) |
| `cancel <thread-id>` | 스레드 하나의 대기 중인 재개를 취소하고 그 스레드를 끕니다 |
| `logs` | 최근 로그 줄 (`-n N`) |
| `run` | 워처를 포그라운드에서 실행 (`--once`, `--poll N`) |
| `stop` | 실행 중인 워처에 종료 요청 |
| `install` | 소유 디렉터리와 상태 생성 (`--startup`) |
| `uninstall` | 자동 시작과 소유한 상태·로그 제거 (`--keep-logs`, `--keep-state`) |
| `diagnostics` | 공유하기 전에 읽어 볼, 민감한 값을 가린 진단 파일 하나를 씁니다 (`--out`) |
| `downgrade-state --to 4` | v0.6.11부터 v0.6.14까지의 릴리스와 v0.6.15 핫픽스가 읽을 수 있게 상태 파일을 다시 씁니다. 먼저 워처를 멈추거나 아래처럼 `--stop-watcher`를 쓰세요. 바꾸는 방식은 `--to 3`과 같으며, *다른 버전 설치...*가 이것을 씁니다 |
| `downgrade-state --to 3` | v0.6.0부터 v0.6.10까지의 릴리스가 읽을 수 있게 상태 파일을 다시 씁니다. 먼저 워처를 멈추세요. 이미 나갔을 수 있는 이어서 하기 메시지는 끝난 것으로 표시하고, 사용자의 확인을 기다리던 대화와 Codex가 아직 이어서 하기 메시지를 전달할 수 있는 대화는 끕니다. `--stop-watcher`를 주면 대신 워처에게 멈추라고 요청하고 최대 1분 기다리며 절대 강제로 끝내지 않고, 한 일을 한 줄로 말합니다. *다른 버전 설치...*가 이것을 씁니다 |
| `downgrade-state --to 2` | v0.5 릴리스가 읽을 수 있게 상태 파일을 다시 씁니다. 먼저 워처를 멈추세요 |
| `compat` | Codex 호환성 레지스트리가 이 Codex에 대해 말하는 것을 워처의 마지막 보고에서 보여 줍니다 (`--live`는 지금 확인하고 아무것도 쓰지 않음, `--json`, `--import FILE`은 데이터 파일을 검증해 통과할 때만 보관) |

전역 옵션: `--home`(이 도구가 자기 상태를 두는 곳), `--codex-exe`, `--codex-home`, `--quiet`.

기본값으로는 `enable`을 실행한 시점에 6시간이 지나지 않은 실패까지 대상이 됩니다.
`enable --lookback-hours N`으로 바꿀 수 있습니다.

## 알림

워처가 중단을 기록하면 작업 이름이 적힌 알림 하나를 보여 줍니다. v0.6.5부터 이 알림은
알림 영역 옆에 제품 자신의 디자인으로 된 카드로 나타나며, Windows 알림과 같은 말과 같은 단추를 담고,
카드가 보인 뒤에는 같은 알림이 조용히 Windows 알림 센터에 더해집니다. 카드가 나타나면 안 될 때는 대신
Windows 자체 알림을 보여 줍니다. **알림 영역 옆에 알림을 카드로 표시**(설정 > 일반 > Windows)가 꺼져
있을 때, 방해 금지나 집중 모드가 켜져 있을 때, 전체 화면 앱 위에서, 세션이 잠겨 있거나 원격일 때, 화면
읽기 프로그램이 실행 중일 때, 알림 영역 아이콘이 꺼져 있을 때입니다.

```
Payment retry refactor
Codex 사용량 한도에 도달했습니다. 05:56에 이 작업을 자동으로 재개합니다.
example-project  ·  대화: 0a1b2c3d-0109-7000-8000-000000000109
                         [재개하지 않음]   [대시보드 열기]
```

첫 줄은 대화 제목, 없으면 프로젝트, 없으면 작업 폴더 이름, 그것도 없으면 "Codex 작업"입니다.
**정확한 스레드 UUID는 항상 표시합니다.** 제목은 겹칠 수 있지만 식별자는 겹치면 안 되기
때문입니다. 일시적인 실패일 때는 어떤 종류였는지를 밝혀 "네트워크 문제 · Codex 작업이 일시적으로
중단되었습니다. 자동으로 다시 시도합니다."라고 적고, **다시 시도하지 않음** 버튼과 함께 보여 줍니다.

Windows는 세 줄까지만 그리고 나머지는 버리므로, 네 줄이 아니라 세 줄이고, 이유가 식별자보다
앞에 옵니다.

이 이름들은 표시용일 뿐입니다. 복구는 제목·프로젝트·최근 여부로 대화를 고르지 않습니다.

아무것도 하지 않으면 재개됩니다. 그것이 기본값입니다. **재개하지 않음** / **다시 시도하지 않음**은
그 중단 하나와 그것을 이어받는 것의 자동 재개를 취소할 뿐, 다른 것은 건드리지 않습니다.
**대시보드 열기**는 대시보드의 대기 중 페이지를 열고 그 밖의 일은 하지 않습니다.

v0.6.16부터는 알림 자체를 클릭하면 - 카드의 겉면이든 Windows 자체 알림의 본문이든 - 그 알림이 다루는
대시보드 페이지가 열립니다. **대시보드 열기** 단추가 여는 페이지이고, 그 단추가 없는 알림이면 이어서 하기를
보내는 동안에는 대기 중, 끝난 뒤에는 기록, 전원 동작의 알림은 설정, 그 밖에는 개요입니다. 그러고 나면 카드는 클릭할 때 늘 그랬듯 물러납니다. 오른쪽
클릭은 카드를 치우기만 하고, 단추들은 늘 하던 일을 그대로 합니다.

알림은 잠시 뒤 저절로 사라집니다. 설정 > 일반 > 알림의 **클릭할 때까지 화면에 두기**에는 알림의 종류가
하나씩 나옵니다. 중단 감지, 복구 시작, 재개됨, 재개할 수 없음, 시도 중단, 취소됨, 대화에 사용자가 필요할
때, 오랜 절전 뒤 기다리는 작업, 워처의 메모리, 사용량 한도 복구가 끝난 뒤의 전원 동작이 있고, 고급판은
사용량 미터의 경고와, 한도 근처에서 멈추기의 세 가지 알림과, 일주일에 한 번 하는 업데이트 확인이 새 버전을 알리는 알림을 하나씩 더합니다. 여기서 고른 종류는 클릭할 때까지, 또는 더 새로운 알림이 자리를 필요로 할 때까지 화면에 남습니다(카드는 최대 셋이 쌓이고 가장 오래된
것이 밀려납니다). 카드는 알림 영역 옆에
머물고, Windows 자체 알림은 닫을 때까지 남는 미리 알림이 되며, 단추가 없는 알림에는 닫는 단추가 붙습니다.
처음에는 아무것도 고르지 않은 상태입니다.

v0.6.11부터는 대화가 먼저 더 물어보게 할 수 있고([조용한 시간과 대화를 이어 가는 방식](#조용한-시간과-대화를-이어-가는-방식)),
그때 알림은 재개를 약속하는 대신 그렇게 말합니다. 사용자를 기다리는 중단은 대시보드에서 이어 가도록
허용하기를 기다린다고 말하고, 알림만 하는 대화의 중단은 자동으로 재개하지 않는다고 말합니다. 이의 제기
기회가 있는 대화는 이어서 할 메시지를 보내기 직전에 알림을 하나 더 받습니다. "멈추지 않으면 14:07에
이어서 진행합니다"라는 알림이고, 버튼은 같은 두 개입니다. 어느 버튼도 무언가를 보내게 할 수는 없습니다.

필요한 순간에 제어를 내밀 수 있는 곳은 여기뿐입니다. 사용량 한도가 Codex 앱에 나타날 때는 그 턴이
이미 실패한 뒤라서 앱 자체의 사용량 한도 안내에는 아무것도 덧붙일 수 없지만, 워처는 그때도 실행
중입니다. 그 안내 자체에 체크박스를 넣을 수 없는 이유는
[docs/PLUGIN.ko.md](PLUGIN.ko.md)에
있습니다.

비슷한 선택을 두 곳에서 더 할 수 있으며, 둘 다 옆에 표시된 바로 그 중단과 대화에 묶여 있습니다.
알림 영역 팝업의 작업마다 붙은 **자동 재개** 스위치와, 대시보드 대기 중 페이지의 **자동 재개** 열입니다.
이 스위치는 그 중단 하나를 취소하는 것이 아니라, 그 작업이 속한 대화의 자동 복구를 다시 켤 때까지
끕니다. 누르는 사이에 끝났거나 사라졌거나 다른 대화의 것으로 밝혀진 작업에 대한 클릭은
거절되고 아무것도 바꾸지 않습니다. 세 곳 모두 무엇도 보내지 않습니다. 워처가 이어 가도 되는지만
바꾸고, 보내기 전에는 워처가 여전히 모든 것을 확인합니다.

알아 둘 점:

- 버튼에는 처리기가 필요하므로 `install`이 사용자별 `codex-auto-resume:` URL 프로토콜을
  `HKCU\Software\Classes`에 등록합니다. `uninstall`은 그것이 이 설치본을 가리킬 때만 다시 지웁니다.
- 이 프로토콜이 받는 동작은 정확히 두 가지입니다. 재개 하나를 취소하는 것과, 정해진 목록에 있는
  대시보드 페이지 하나를 여는 것입니다. 악의적이거나 잘못 입력한 URI가 할 수 있는 일은 재개를
  *멈추거나* 창을 여는 것뿐이며, 재개를 *발생시킬* 수는 없고, 중단 id는 실제 기록과 맞아야 합니다.
- 알림에는 표시용 이름, 로컬 시각, 스레드 UUID만 나오고 프롬프트 내용, 오류 본문, 계정 정보는
  나오지 않습니다. 중단 종류는 분류된 범주에 대한 이 제품의 레이블이지 오류 문장이 아닙니다. 표시
  이름은 `threads.name`에서만 가져오며, 이 스키마에서 원래의 첫 프롬프트를 담는 `title`, `preview`,
  `first_user_message`는 읽지 않습니다.
- 알림은 화면 언어로 표시됩니다.
- 최선을 다해 보여 줄 뿐입니다. 보여 줄 수 없어도 재개는 원래대로 일어납니다.
- 보내는 주체는 **Codex Auto Resume**으로 표시되고 이 프로젝트의 아이콘이 함께 나옵니다. PowerShell이나
  Python 이름은 보이지 않습니다. 여기에는 등록이 하나가 아니라 두 가지 필요합니다.
  `HKCU\Software\Classes\AppUserModelId` 아래의 AppUserModelID가 이름과 아이콘을 정하고, 같은 ID를
  단 시작 메뉴 바로 가기가 있어야 Windows가 토스트를 화면에 그립니다. 바로 가기가 없으면 Windows는
  알림을 받아들여 기록하고 알림 센터에 넣기까지 하지만, 화면에는 끝내 보여 주지 않습니다. 추측이
  아니라 실측한 결과입니다.

이후 세 가지 알림이 더 있습니다. 복구 시작, 결과, 그리고 복구를 완전히 중단했을 때. 각각 상태 변화
자체에서 한 번만 발생하므로 알림 내용과 기록된 상태가 어긋날 수 없습니다. 전송 여부가 불확실한 것은
다시 시도할 실패가 아니라 불확실하다고 알립니다. 일부러 절대 다시 보내지 않는 유일한 결과이기
때문입니다.

어느 알림이든 대시보드에서, Codex에서, 또는 `update_settings`로 끌 수 있습니다. 끄더라도 작업이
복구되는지는 달라지지 않습니다.

### 대화에 사용자가 필요할 때

v0.6.11부터 워처는, 사용자만 이어 갈 수 있어서 이 제품이 결코 이어 가지 않는 대화에 대해서도 알려 줄
수 있습니다. 기본으로 꺼져 있으며, 설정 > 일반 > 알림에서 **대화에 사용자가 필요할 때**를 켜면 됩니다. 그
종류와 시간과 소리는 그 아래에 있고, 이것이 켜져 있을 때 바꿀 수 있습니다. 그러면:

- 다시 시도하지 않는 실패마다 종류를 한마디로, 다음에 할 일을 한 가지 적은 알림이 한 번 옵니다. 요청이
  거절되었거나 대화가 너무 긴 경우("요청이 거절됨 · 대화가 너무 긴가요? Codex에서 압축하거나
  새 대화를 시작하세요."), 콘텐츠 정책이 턴을 멈춘 경우, Codex에
  다시 로그인해야 하는 경우, Codex가 턴을 포기한 경우입니다. 종류마다 있는 체크박스로 넷 가운데 무엇을 알릴지
  고릅니다. 사용자가 직접 멈춘 턴은 결코 알리지 않습니다.
- **턴에 변화가 없는 시간**을 10분에서 2시간 사이로, 또는 직접 정한 시간으로 정해 두면, 마지막 턴이 아직 진행 중인데 그 시간 동안
  새로 기록된 것이 없는 대화에 대해서도 알림이 한 번 옵니다. "이 턴에 20분 동안 새로 기록된 것이 없습니다.
  Codex에서 확인해 보세요." 아는 것은 그것뿐입니다. 턴 자신의 열과 가장 최근 항목이 기록된 시각만 읽고 어떤
  항목의 내용도 읽지 않으므로 이유는 말하지 않으며, 그 턴은 단지 아직 작업 중일 수도 있습니다.

각 알림은 워처가 몇 번을 살펴보든, 다시 시작하더라도 한 번만 오며, 자동 복구가 켜져 있는 대화에 대해서만,
복구가 일시 정지되지 않았을 때에만 옵니다. 일주일이 넘은 실패는 알리지 않습니다. 이 가운데 어느 것 때문에도
이어 가거나 보내거나 복구로 기록하는 것은 없습니다. 알림의 단추는 **대시보드 열기** 하나이며, 대시보드의
설정 페이지를 엽니다. 종류를 끄는 곳이 그 페이지이고, 알림 자체는 어떤 설정도 바꾸지 않습니다. **이 알림에
소리 내기**를 켜면 이 알림에 Windows의 미리 알림 소리가 납니다. 그때는 카드가 켜져 있어도 언제나 Windows
자체 알림으로 나타나는데, 카드는 소리를 내지 않기 때문입니다. 방해 금지는 다른 알림처럼 이 알림도
보류합니다. 끄면 소리가 나지 않습니다.

## 설정

설정할 수 있는 것은 모두 한곳에 있고, 세 가지 방법으로 닿을 수 있습니다.

- **시작 메뉴 → Codex Auto Resume** — 대시보드의 설정 페이지입니다. Codex가 닫혀 있거나,
  플러그인이 꺼져 있거나, 네트워크·로그인·시스템 Python이 없어도 동작합니다. 설정은 설정하는
  대상이 쓸 수 없을 때 가장 필요하기 때문입니다.
- **Codex 안에서** — 자동 재개 설정을 열어 달라고 하면 대화 안에 패널이 나타납니다.
- **명령줄** — 스크립트와 복구용입니다.

세 곳 모두 같은 검증기를 거쳐 같은 파일에 쓰므로, 한곳에서 정한 값이 다른 곳에도 그대로
보입니다. 손으로 고칠 필요는 없습니다. 직접 편집한 설정 파일은 읽을 때 검증되어, 잘못된 값은 절반만 적용되는 대신 안전한
기본값으로 바뀝니다.

설정 페이지는 다섯 부분으로 나뉩니다.

| 부분 | 들어 있는 것 |
| --- | --- |
| 일반 | 화면 언어, **Windows 로그인 시 실행**, 알림 영역 아이콘, v0.6.11부터 작업이 기다리는 동안 이 PC 깨워 두기와 워처의 메모리 보호, 다른 도구용 상태 파일, 표시할 알림. v0.6.11부터는 대화에 사용자가 필요할 때의 알림도 |
| 자동 복구 | 분류된 중단 가운데 어떤 종류를 복구할지. 종류마다 체크박스가 하나씩 있습니다. v0.6.11부터 지켜보기만도 여기 있습니다 |
| 이어서 하기 메시지 | Codex에 보내는 메시지의 언어와 스타일, 직접 입력 메시지, 실제 문장 미리보기 |
| 모양 | 테마(시스템 설정 따르기, 밝게, 어둡게), 패널의 Codex 안의 테마, 디자인(부드럽게, 클래식 (v0.6.2), 단순하게), 움직임 줄이기 |
| 고급 | 중단당 시도 횟수, 진전 없는 복구 뒤 멈출 시점, 작업당 이어서 하기 횟수, 재시도 간격, 그리고 v0.6.11부터 조용한 시간, 대화를 이어 가는 방식, 처음 보는 대화에 줄 것, 이어 가도 되는 프로젝트, 직접 설정한 재시도 대기와 지터, 시간 상한, 작업 변경 보호와 컨텍스트 비용 보호, 오래 절전한 뒤 기다리게 할 것, 인터넷 연결 기다리기 - 그리고 v0.6.16(처음에는 v0.6.15-beta로 공개)부터 지켜볼 [Codex 홈](#여러-codex-홈) |

워처가 복구하는 종류에는 모두 체크박스가 있고 기본으로 체크되어 있습니다. v0.6.3부터 v0.6.9까지는
로그인 서비스를 일시적으로 쓸 수 없는 경우(`auth_service_transient`)의 **로그인 서비스 오류** 체크박스가 하나
더 있었고, 이 안내서는 그 종류가 v0.6.2까지 끌 방법 없이 복구되었다고 적었습니다. 그런 적은 없습니다.
Codex가 기록하는 어떤 오류도 그 종류로 분류된 적이 없어서, 그 체크박스는 아무것도 바꿀 수 없었습니다.
v0.6.10부터 그 체크박스는 직접 입력 메시지와 함께 없어졌고, 그 종류는 실제 Codex 오류가 그것을 담고
있는 것이 확인되어야만 돌아옵니다.

스위치는 동작하는 무언가를 켜고 끕니다(알림, 알림 영역 아이콘, 움직임 줄이기, **Windows 로그인 시 실행**, 대화 하나의
자동 복구). 체크박스는 목록에서 어떤 항목을 적용할지 고릅니다(위의 중단 종류, 표시할 알림).
같은 설정은 대시보드와 패널에서 같은 종류입니다.

안전 속성은 설정이 아니므로 끌 수 없습니다. 분류되지 않은 실패를 다시 시도하거나, 제목으로
대화를 고르거나, 전송 여부가 불확실한 것을 다시 보내거나, 강제로 보내는 옵션은 없습니다.
빠뜨린 것이 아니라 일부러 그렇게 만들었습니다.

### 직접 정한 값: 직접 입력...과 무제한

v0.6.11부터 값을 고르는 드롭다운(대기 시간, 시각, 조용한 시간이 시작하는 요일, 시간이나 메가바이트, 토큰
수)은 모두 맨 끝에 **직접 입력...**이 있습니다. 대시보드와 Codex 안의 패널이 같습니다. 목록 밖의 값을 직접 정할
수 있고, 정할 수 있는 범위를 함께 보여 줍니다.

| 설정 | 직접 입력...으로 정할 수 있는 값 |
| --- | --- |
| 조용한 시간 시작, 조용한 시간 끝 | 하루 중 아무 분이나, 00:00~23:59 |
| 조용한 시간 요일 | 월요일부터 일요일까지 체크한 요일 |
| 직접 설정: 첫 번째 대기 | 5초~2시간 |
| 직접 설정: 두 번째~다섯 번째 대기 | 15분~6시간, 분 단위 |
| 계속 실패하는 작업을 멈추기까지 | 15분~7일, 분 단위 |
| 대화가 사용한 토큰(넘으면 보류) | 10,000~10,000,000, 천 단위 |
| 턴에 변화가 없는 시간 | 5분~7일, 분 단위 |
| 이보다 오래 절전한 뒤에는 먼저 묻기 | 5분~7일, 분 단위 |
| 깨워 두는 최대 시간 | 15분~7일, 분 단위, 또는 **무제한** |
| 너무 많은 메모리의 기준 | 128~16384MB |

대시보드에서 직접 입력...을 고르면 작은 대화 상자가 열립니다(숫자와 단위, 시와 분, 또는 일곱 요일). **이 값
사용**을 누르면 드롭다운에 값을 보여 주기 전에 설정 자체의 검증기에 묻고, 받아들이지 않는 값이면 대화 상자에
범위와 함께 그렇다고 알리며 아무것도 바꾸지 않습니다. 패널에서는 같은 입력란이 설정 아래에 열리고, 다른 모든
변경처럼 저장할 때 같은 검증기가 답합니다. 값은 가장 짧은 정확한 형태로 저장됩니다. 60분은 1시간으로, 선택지
하나가 가리키는 요일 묶음은 그 선택지로 저장되므로, 저장된 두 값이 같은 것을 뜻하는 일은 없습니다.

통계 페이지의 **기간**(최근 7일, 최근 30일, 전체)에는 직접 입력...이 없습니다. 그 페이지가 얼마나 지난 것까지
셀지만 정할 뿐 설정이 아니고 어디에도 저장되지 않으므로, 창은 열 때마다 최근 7일로 시작합니다.

**무제한**은 한도가 오로지 사용자의 것일 때만 있습니다. 작업이 기다리는 동안 이 PC를 깨워 두는 시간이 그렇고,
무제한이면 작업이 기다리는 동안 계속 깨워 둡니다. 기다리는 것이 없을 때, 복구를 일시 정지했을 때, 워처가 멈출
때는 늘 그랬듯이 요청을 거둡니다. 다른 목록은 모두 이미 **끔**으로 시작하고, 끔이 곧 한도 없음이므로 같은
결과에 두 가지 길을 두지 않습니다. 복구를 안전하게 지키는 한도에는 무제한도, 범위를 넘는 값도 없습니다. 재시도
대기는 목록의 처음과 끝 사이에 머물고, 시도 횟수 예산은 범위 안의 숫자로 남으며, 워처 자체의 하한(한 대화에
15분에 한 번, 24시간에 다섯 번)은 아예 설정이 아닙니다.

전에 쓴 설정 파일은 그대로 읽힙니다. 이전 버전은 직접 정한 값을 그 설정의 기본값으로 읽습니다.

### 조용한 시간과 대화를 이어 가는 방식

v0.6.11부터 고급 아래의 설정 두 가지가 복구를 더 붙잡아 둘 수 있습니다. 둘 다 기본으로 꺼져 있고,
그때 워처는 늘 하던 대로 움직입니다. 어느 쪽도 무언가를 더 일찍 보내게 하거나 확인을 건너뛰게 할 수
없습니다.

**조용한 시간**(시작, 끝, 시작하는 요일. 각각 선택지에서 고르거나 직접 입력...으로 아무 분, 아무 요일이나)은
그 안에서 예정 시각이 된 복구를 조용한 시간이 끝날 때까지 기다리게 합니다. 자정을 넘기는 시간은 시작하는 날에 속하고, 시각은 서머타임이 바뀌는 날에도 사용자의
시계를 따릅니다. 조용한 시간은 풀리지 않는 사용량 한도를 포기하기까지의 시간에 넣지 않습니다. *기다리는
이유*에는 "08:00까지 조용한 시간"이라고 나옵니다.

**대화를 이어 가기 전에**는 따로 고르지 않은 대화가 먼저 얼마나 물어볼지를, 고른 뒤에 감지되는
중단부터 정합니다. 작업 행의 메뉴에서는 그 대화에만 따로 고릅니다.

| 선택 | 일어나는 일 |
| --- | --- |
| 자동으로 이어 가기 | 늘 하던 대로, 모든 확인을 거친 뒤 이어서 할 메시지를 보냅니다. 기본값입니다. |
| 이의 제기 기회 후 | 다른 모든 것이 보내도 된다고 할 때 언제 보낼지 알림으로 알리고, **이의 제기 시간**(1~60분, 기본 5분)이 지나야 보냅니다. 재개하지 않음으로 멈출 수 있습니다. 이의 제기 시간이 열리기 전에 미룬 작업은 그만큼 늦춰질 뿐이고 그 뒤에 이의 제기 시간이 그대로 열리며, 이의 제기 시간 중에 미룬 작업은 고른 시각에 보냅니다. **미루지 않기**는 이의 제기 시간의 시각으로 되돌릴 뿐, 그보다 앞당기지 않습니다. |
| 먼저 묻기 | 대시보드나 팝업의 그 행에서 **이어 가도록 허용**을 고를 때까지 아무것도 보내지 않습니다. |
| 알림만 | 같고, 알림은 자동으로 재개하지 않는다고 말합니다. |

대화에 먼저 묻기나 알림만을 고르면 그 대화에서 기다리는 것도 붙잡아 둡니다. 덜 묻는 방식을 골라도
이미 사용자를 기다리는 것은 풀리지 않으며, 그런 작업마다 **이어 가도록 허용**이 따로 필요합니다. 그 뒤에도
미룬 시각과 조용한 시간은 그대로 적용됩니다.

### 지켜보기만, 그리고 어떤 대화와 프로젝트를 이어 갈지

v0.6.11부터 설정 세 가지가 복구를 더 붙잡아 둘 수 있습니다. 모두 기본으로 꺼져 있고, 그때 워처는 늘
하던 대로 움직입니다. 어느 것도 무언가를 더 일찍 보내게 하거나 확인을 건너뛰게 할 수 없습니다.

자동 복구 아래의 **지켜보기만**은 보내는 것만 빼고 워처가 모든 일을 하게 합니다. 모든 확인은 그대로 하고,
보냈을 복구는 그렇다고 보여 줍니다. 대기 중과 기록의 그 행에는 "보냈을 것"과 그 시각이 나오고, *기다리는
이유*는 지켜보기만을 뺀 모든 확인을 통과했다고 말하며, 진행 기록에는 그렇게 될 때마다 한 번씩 남습니다.
개요는 자동 복구가 켜짐이라고 말하던 자리에 지켜보기만이라고 말하고, 팝업도 그렇게 말합니다. 아무것도
보내려고 잡아 두지 않고 아무것도 보내지 않습니다. 워처는 설정을 보고 거절하고, 워처가 두는 복구 상태에도
설정에서 옮겨 적는 따로 된 스위치가 있어 그것만으로도 모든 전송을 거절합니다. 켤 때 이미 Codex의 대기열에
들어가 있던 이어서 하기 메시지는 일시 정지할 때처럼 다시 거둬들입니다. 그래도 Codex가 시작해 버렸다면 진행 기록은
지켜보기만이 켜져 있었지만 실행되었다고 말하며, 복구가 일시 정지되어 있었다고는 말하지 않습니다. 끄면 복구가 다시 보냅니다.

고급 아래의 **처음 보는 대화**는 기본으로 다른 대화처럼 이어 갑니다. **알림만**을 고르면 이 제품이 한 번도
본 적 없는 대화는 첫 중단이 감지될 때 그 선택을 자기 선택으로 갖게 되어, 작업을 이어 가도록 허용하거나 그
작업의 행에서 이어 가는 방식을 바꾸기 전까지 아무것도 보내지 않습니다. 이미 본 대화는 가지고 있던 것을
그대로 둡니다.

고급 아래의 **이어 가도 되는 프로젝트**는 기본으로 모든 프로젝트입니다. **이어 가기를 허용한 프로젝트만**은
작업 행에서 **이 프로젝트 이어 가기 허용**으로 정한 프로젝트의 작업만 묻지 않고 이어 가게 하고, **보류한
프로젝트를 뺀 모든 프로젝트**는 **이 프로젝트 보류**로 정한 프로젝트만 빼고 이어 가게 합니다. 기본값에서 이
프로젝트 보류를 고르면 두 번째로 바뀝니다. 그 밖의 프로젝트나 프로젝트를 읽을 수 없는 작업은 감지될 때 알림만과
같이 사용자를 기다리며, 버려지지 않습니다. **이어 가도록 허용**으로 보낼 수 있습니다. 행에서 프로젝트를
보류하면 그 프로젝트에서 기다리는 것도 붙잡아 두고, 이어 가기를 허용해도 이미 사용자를 기다리는 것은 풀리지
않습니다. 프로젝트는 Codex가 대화를 넣어 둔 프로젝트, 없으면 대화가 작업하는 폴더이며, 설정에는 그것의
64자리 다이제스트만 남고 이름이나 경로는 남지 않습니다. 기본값에서는 이 일로 Codex의 프로젝트를 읽지도
않습니다.

### 직접 정한 대기, 시간 상한, 두 가지 보호

v0.6.11부터 고급에 네 가지가 더 있습니다. 모두 기본으로 꺼져 있거나 쓰이지 않으며, 그때 워처는 늘
하던 대로 기다리고 보냅니다. 어느 것도 무언가를 더 일찍 보내거나 확인을 건너뛰게 할 수 없고, 복구를 더
오래 기다리게 하거나, 더 일찍 멈추게 하거나, 사용자를 기다리게 할 뿐입니다.

**재시도 간격**에 **직접 설정**이 생깁니다. 일시적인 오류로 실패한 작업에 대해 목록에서 고르거나, 직접
입력...으로 각 목록의 범위 안에서 직접 정하는 다섯 가지 대기입니다. 첫 번째는 작업의 첫 이어서 하기 전에, 두 번째는 같은 작업의 이어서 하기가 다시 실패한 뒤에 오는
식이고, 다섯 번째는 그 뒤 모든 시도에 씁니다. 첫 번째는 5초까지 짧게 할 수 있고, 그다음부터는 15분에서
시작합니다. 15분은 설정이 아닌 워처 자체의 하한으로, 무엇을 고르든 한 대화에는 15분에 한 번, 24시간에 다섯
번까지만 이어서 하기를 보냅니다. 요청 제한의 첫 대기는 여전히 최소 1분이고, Codex의 구조화된 오류가 대기
시간(Retry-After)을 알려 주면 첫 대기는 그보다 짧아지지 않습니다. 다만 그런 값을 쓰는 Codex 빌드는 아직 본
적이 없습니다. 대기 아래의 한 줄은 이어서 할 때마다 곧바로 실패한다면 고른 간격이 실제로 얼마가 되는지
보여 주고(보통이라면 5초, 그 뒤로는 각각 약 15분), Codex 안의 패널도 똑같이 보여 줍니다. **대기마다 최대
5분의 1 더하기**(지터)는 일시적 실패의 모든 대기를 최대 5분의 1까지 무작위로 늘리며, 줄이지는 않습니다.

**계속 실패하는 작업을 멈추기까지**는 기본으로 꺼져 있습니다. 1~24시간을 고르거나 15분~7일 사이에서 직접
정하면 일시적 실패가 그보다 오래 이어진 작업을 멈춥니다. 작업의 첫 실패부터 가장 최근 실패까지 재되, 재시도 자체가 아닌 것을 기다린 시간은
뺍니다. 일시 정지, 미뤄 둔 시간, 이의 제기 시간, 조용한 시간, 앱을 기다린 시간은 세지 않고, 재시도 대기와
두 번의 이어서 하기 사이 15분은 셉니다. 시도 횟수를 다 쓴 것처럼 작업을 멈추고(**시도 횟수 되돌리기**는 시간도
되돌립니다), 사용량 한도에는 적용되지 않습니다.

**기다리는 동안 작업이 바뀌었다면**(작업 변경 보호)은 이어서 할 메시지를 보내기 직전에 대화의 모델과 승인
모드, 폴더의 git 브랜치나 커밋을 멈췄을 때와 비교합니다. 브랜치나 커밋은 폴더의 `.git/HEAD`를 파일로 읽은
것이며 git은 실행하지 않습니다. **보류**는 바뀐 작업을 사용자가 허용할 때까지 기다리게 하고(**이어 가도록
허용**하면 보내며, 그 뒤 또 바뀌어야 다시 보류합니다), **이어 가고 알려 주기**는 보내면서 알림에 작업이
바뀌었다고 알려 줍니다. 멈췄을 때는 읽을 수 있었는데 지금은 읽을 수 없는 폴더는 바뀐 것으로 보고,
네트워크 공유 경로로 된 폴더는 아예 읽지 않습니다. 세 가지의 다이제스트만 남습니다. 고른 뒤에 감지되는
중단부터 적용됩니다.

**대화가 사용한 토큰**(컨텍스트 비용 보호)은 Codex의 대화 목록이 숫자로 보관하는 경우, 중단이 감지될 때
Codex가 직접 센 값을 읽습니다. **대기 중에 표시**는 작업 옆에 개수를 보여 주고, **100,000~1,000,000 넘으면
보류**(또는 직접 정한 개수)는 대화가 그보다 많이 사용한 작업을 처음부터 사용자를 기다리게 합니다. Codex가 그런 개수를 보관하지
않으면 이 보호는 아무것도 하지 않습니다. 고른 뒤에 감지되는 중단부터 적용됩니다.

**중단당 시도 횟수**, **진전 없는 턴이 이만큼 이어지면 중지**, **작업당 이어서 하기 횟수**를 각각 8, 5, 8보다
높게 두면 대시보드와 패널에서 그 아래에 안내가 나타납니다. 그러면 계속 실패하는 작업이 여러 번 이어질 수
있고, 이어서 할 때마다 Codex 사용량을 씁니다.

### 절전, 이 PC 깨워 두기, 인터넷

v0.6.11부터 세 가지가 더 있으며, 모두 기본으로 꺼져 있습니다. 꺼져 있으면 워처는 이를 위해 Windows에
아무것도 묻지 않고 늘 하던 대로 기다립니다. 켜 두어도 어느 것도 무언가를 보내거나, 확인을 건너뛰거나, 복구를
제 시각보다 일찍 보내지 않습니다.

고급의 **이보다 오래 절전한 뒤에는 먼저 묻기**(30분~12시간, 또는 직접 정한 시간)는 이 PC가 그보다 오래 절전하는 동안 예정 시각이 된
대기 중인 복구를 모두 사용자를 기다리게 합니다. 알림 하나가 얼마나 절전했는지와 몇 개의 작업이 기다리는지
알려 주며, 단추는 대기 중을 여는 **대시보드 열기** 하나뿐입니다. 작업마다 **이어 가도록 허용**하면 보내고,
**취소**하면 멈춥니다. *기다리는 이유*는 PC가 절전하는 동안 예정 시각이 되었다고 알려 줍니다. 얼마나
절전했는지는 워처의 두 번의 확인 사이에서, 시계와 PC가 깨어 있던 시간을 Windows가 센 값으로 잽니다. 그래서
Windows가 PC가 깨어났다고 알리기 전에 확인이 먼저 와도 절전을 알아차립니다. 깨어날 때까지 시각이 오지 않은
작업은 기다리게 하지 않습니다.

일반 > Windows의 **작업이 기다리는 동안 이 PC 깨워 두기**(**전원에 연결된 동안만** 또는 **항상**)는 작업이
기다리는 동안 PC가 저절로 절전하지 않도록 Windows에 요청합니다. 작업이 기다리기 시작할 때마다 **깨워 두는 최대
시간**(기본 6시간. 직접 정한 시간이나 무제한도 됩니다)까지만 요청합니다. 워처가 했다가 거두는 요청으로, `powercfg /requests`에 나오는 종류입니다.
기다리는 것이 없을 때, 시간이 다 되었을 때, 복구를 일시 정지했을 때, 워처가 멈출 때 거두며, 어떤 경우든
Windows는 워처와 함께 끝냅니다. 화면은 여전히 꺼질 수 있고, 덮개를 닫거나 절전을 고르면 PC는 그대로 절전하며,
Windows 설정은 바뀌지 않습니다. 전원에 연결된 동안만을 고르면 배터리로 쓸 때는 평소처럼 절전합니다. PC를 깨워
두는 동안 개요가 그렇다는 것과 언제부터인지 알려 줍니다. 대기 아래의 줄에서 마지막 사용량 읽기보다 먼저 말하므로
카드에 줄이 늘지 않습니다. 카드보다 긴 줄은 말줄임표로 끝나고, 줄 전체는 툴팁과 진단의 **작업이 기다리는
동안**에 나옵니다.

둘 중 하나가 켜져 있으면 워처는 PC가 깨어나는 것도 듣고, 다음 확인을 기다리지 않고 곧바로 다시 확인합니다.
그때 Codex 앱과 사용량에 대해 마지막으로 읽은 것은 잊습니다.

고급의 **인터넷 연결 기다리기**는 예정 시각이 된 복구의 Codex 사용량을 읽기 직전에, 이 PC가 인터넷에 연결되어
있는지 Windows에 묻습니다. 묻는 곳은 Windows의 네트워크 목록 관리자로, Windows가 이미 아는 것으로 답하며
아무것도 보내지 않습니다. Windows가 연결이 없다고 알리는 동안에는 복구가 기다리며 1분마다 다시 확인하고,
사용량을 읽으려고 Codex 도우미를 띄우지 않습니다. *기다리는 이유*와 팝업의 그 행은 "인터넷 없음(Windows
기준)"이라고 알려 줍니다. 일부 프록시 뒤에서는 인터넷이 되는데도 Windows가 연결이 없다고 알리므로 기본으로
꺼져 있습니다. Windows에 물을 수 없거나 답이 없으면 사용량은 늘 하던 대로 읽습니다.

### 사용량 한도 복구가 끝나면 절전, 최대 절전 또는 시스템 종료

v0.6.12부터 워처는 모든 사용량 한도 복구가 끝나면 이 PC를 절전, 최대 절전 상태로 두거나 시스템을 종료할
수 있습니다. 밤새 돌려 둔 작업이 끝난 뒤가 그런 경우입니다. 기본으로 꺼져 있고, 대시보드에서만 켭니다. 설정 >
일반의 마지막 카드 **사용량 한도 복구가 끝나면**입니다. **동작**(절전, 최대 절전, 시스템 종료), **조건**(모든
복구가 성공했을 때, 각 복구가 성공했거나 사용자에게 넘어갔을 때, 각 복구가 어떻게든 끝났을 때), **반복**(한 번,
다음 사용량 한도에만, 또는 매번), **먼저 알려 줄 시간**(2~30분, 기본 5분)을 고른 뒤, 다른 설정을 켜듯 카드의 스위치를 켭니다. 확인 창이 고른 것을 다시 보여 주며, 기본 단추는 취소입니다. **켜기**로 답하지 않으면 스위치는 꺼진 채로 있습니다. 카드는 곧바로 적용되고, 저장은 이것을
바꾸지 않습니다. 이 PC에서 Windows가 하지 않는 동작은 동작 목록에서 빠지고, 그 이유를 한 줄로 알려 줍니다.
최대 절전은 Windows에서 꺼져 있는 동안(이 제품은 그것을 켜지 않습니다), 절전은 프로그램이 시작할 수 있는 절전
상태가 없다고 Windows가 알리는 동안, 세 가지 모두는 이 계정에 Windows의 시스템 종료 권한이 없는 동안입니다.

**무엇을 세는지.** 사용량 한도에서 온 복구만 이것을 시작하고 결정합니다. 연결 오류, 시간 초과 같은 일시적인
실패에서 온 복구는 그러지 않지만, 그런 복구가 기다리거나 도는 동안에는 전원 동작도 붙잡아 둡니다. 세는 복구는
켤 때 기다리던 사용량 한도와 그 뒤에 감지된 모든 사용량 한도이며, 복구된 작업이 다음에 부딪친 한도도
들어갑니다. **한 번**은 이 묶음에 쓰이고, 하루 안에 사용량 한도가 오지 않으면 스스로 꺼집니다. **매번**은 묶음이
끝날 때마다 다시 시작합니다.

**언제 동작하는지.** 확인할 때마다 이 순서로 봅니다. 알림에서 누른 멈춤은 그 묶음을 끝내며, 아무 일도 일어나지
않습니다. 일시 정지, 지켜보기만, 관리자의 `DisablePowerAction`은 이것을 붙잡아 둡니다. 묶음의 모든 복구가
끝났고, 아직 기다리거나 돌거나, 이어서 하기 메시지가 아직 도착할 수 있어 지켜보는(최대 하루) 복구가 없어야
합니다. 복구가 **조건**에서 고른 대로 끝나야 하며, 그렇지 않으면 동작 없이 묶음이 끝납니다(한 번이면 알림으로
알려 줍니다). Codex가 지난 한 시간 안에 쓰인 모든 대화를 다 기록했고, Codex에서 도는 턴이 없고, 대기 중인 입력이
없어야 합니다. 시스템 종료라면 이 PC에 다른 사람이 로그인해 있지 않아야 합니다. 그리고 2분 동안 아무도 이 PC를
쓰지 않아야 합니다. 카드의 두 번째 줄이 무엇을 기다리는지 알려 줍니다. 그러면 알림이 언제 일어날지 알려 주며,
**절전 안 함**(또는 최대 절전 안 함, 종료 안 함)과 **대시보드 열기** 단추가 있고, 카드도 같은 시각을
보여 줍니다. 어떤 입력이든, 일시 정지, 워처의 확인 사이의 공백, 위의 어느 조건이든 더는 맞지 않게 되면
카운트다운이 끝나고, 모두 다시 맞으면 새 카운트다운이 시작됩니다. 워처가 보기 한 시간도 더 전에 복구가 끝난
묶음은, 예를 들어 다시 시작한 뒤라면, 동작 없이 끝납니다. 시간이 다 되면 워처는 먼저 묶음을 끝난 것으로
기록하고, 마지막 알림으로 알린 뒤 Windows에 한 번 요청합니다. Windows는 거절할 수 있습니다. 시스템 종료는 모든
프로그램에 묻고, 어느 프로그램이든 거절할 수 있습니다. 그러면 알림이 그렇게 알려 주고, 다시 시도하지 않으며,
카드는 Windows가 거절했다고 보여 줍니다.

**끄는 방법.** 아무것도 묻지 않는 카드의 스위치, 켜져 있는 동안 알림 영역 아이콘 메뉴의 **복구 후 절전하지 않기**(또는 최대
절전, 시스템 종료), 그 묶음에 한해 알림의 단추, 또는 Codex에서 도구 `turn_off_power_action`입니다. 이 중 어느
것도 이것을 켤 수는 없습니다. 복구 일시 정지는 끄는 방법이 아닙니다. 전원 동작을 붙잡아 두고 카운트다운을
끝내지만, 복구를 다시 켜면 전처럼 동작합니다. 이것의 알림은 멈추는 방법이기 때문에 알림 스위치와 상관없이 보이지만, Windows의
방해 금지가 여전히 숨길 수 있습니다.

**확인하지 않는 것.** 이 Codex 홈의 Codex만 확인합니다. 다른 프로그램, 다운로드, 재생, 저장하지 않은 작업은
확인하지 않으니, 시스템 종료를 고르기 전에 작업을 저장해 두세요. Codex에 아무것도 보내지 않고, Windows 설정을
바꾸지 않으며, 프로그램을 시작하지 않고, 관리자 권한이 필요 없습니다. 절전과 최대 절전은 Windows의 깨우기
타이머를 그대로 두고, 시스템 종료는 어떤 프로그램도 강제로 닫지 않습니다. 이것이 남기는 것은 파일 하나,
`config\power-action.json`이며, id, 시각, 정해진 낱말만 담고 제목이나 경로는 담지 않습니다.

### 워처의 메모리, 멈춘 방식, 상태 파일

v0.6.11부터 워처는 확인할 때마다 자기 프로세스가 확보한 메모리가 얼마인지 Windows에 묻고, 가장 많이 쓴
양을 기억합니다. 진단은 이를 **최대 메모리**로 보여 줍니다. 기본 설정에서 일어나는 일은 이것뿐입니다. 일반 >
Windows의 **워처가 메모리를 너무 많이 쓸 때**는 기본으로 꺼져 있습니다. **알려 주기**는 한 번 알리고(단추는
진단을 여는 하나뿐) 워처는 계속 실행합니다. **알려 준 뒤 워처 멈추기**는 워처도 멈춥니다. 진행 중인 확인이 끝난
뒤에만, 멈춤 요청과 같은 방식으로 멈추므로 이어서 하기 메시지를 보내는 도중에는 멈추지 않습니다. Windows 자체
알림이 그렇다고 알리며, 단추는 개요를 여는 하나뿐입니다. 기다리던 것은 잃지 않으며, 워처를 저절로 다시
시작하는 것은 없습니다. 로그인 런처도 다시 시작하지 않고, 그렇게 할 다른 프로세스도 없습니다. 준비가 되면
대시보드, 패널, 시작 메뉴에서 다시 시작하세요. 기준은 **너무 많은 메모리의 기준**으로, 256~2048MB(직접 입력...으로는
128~16384MB)이며 기본은 1024MB입니다.

일부러 멈추는 워처(멈춤 요청, 업그레이드, 메모리 보호)는 멈추면서 그렇다고 남깁니다. 같은 Windows 로그인에서
그런 말 없이 사라진 워처는 진단과 Codex 안의 패널에 마지막으로 확인된 시각과 함께 **예기치 않게 멈춤**으로
나오고, 메모리 보호가 멈춘 워처는 그 시각과 함께 **메모리 보호로 멈춤**으로 나옵니다. 개요의 지금 카드는 같은
말을 시각 없이 하며, 시각은 바로 아래 마지막 확인이 알려 줍니다. 이전 로그인에서, 또는
Windows가 마지막으로 시작되기 전에 끝난 워처는 전처럼 **실행 중 아님**으로만 나옵니다. 그때는 Windows가 끝낸
것이니 뜻밖의 일이 아닙니다.

일반 > Windows의 **다른 도구용 상태 파일 쓰기**는 기본으로 꺼져 있습니다. 켜면 워처가 확인할 때마다, 그리고
멈출 때 한 번 더 설정 폴더(`config\`)에 `status.json`을 씁니다. 워처가 실행 중인지, 복구가 켜져 있는지·일시
정지했는지·지켜보기만 하는지, Codex 엔진의 호환성 단어, 상태마다 대기 중인 복구 수와 다음 확인 시각, 마지막으로 읽은
Codex 사용량(개요가 보여 주는 것과 같은 숫자)이 들어 있습니다. 대화나 기록의 ID, 이름이나 제목, 경로는 들어 있지
않고, 통째로 쓰거나 아예 쓰지 않으며, 이 제품은 이 파일을 읽지 않습니다. 직접 만든 상태 표시줄이나 스크립트가
포트나 서버 없이, 이 제품에 묻지 않고 읽으라고 있는 파일입니다. `running`이라고 적힌 채 몇 분째 바뀌지 않는
파일은 사라진 워처의 것입니다. 끄면 파일을 지웁니다.

### 진단: 로그, 상태 폴더, 어떻게 되는지 보기

v0.6.11부터 진단 페이지에 세 가지가 더 있습니다. 모두 볼 때만 묻고, 어느 것도 아무것도 바꾸지 않습니다.

**로그 검색...**은 이 제품의 로그(로그 폴더 열기가 보여 주는 것)를 검색 상자와 함께 엽니다. 입력한 말이 든
줄, 또는 모든 줄을 최신 줄이 맨 아래에 오게 보여 주며, 열려 있는 동안 5초마다 다시 봅니다. 로그는 정해진 문장
표에서만 쓰므로 사유 코드, 대화 ID, 시각만 있고 프롬프트, 답변, 오류 문구는 없습니다. 예외 메시지를 그대로
남기는 `errors.log`는 여기서 읽지 않습니다.

상태 아래의 **상태 폴더**는 설정, 대기 중인 작업, 로그가 있는 폴더를 Windows가 누구에게 열어 주는지 말합니다.
**내 계정만 열 수 있음**(모든 사용자 폴더가 그렇듯 Windows 자체와 이 PC의 관리자와 함께), **이 PC의 다른 계정도
열 수 있음**(무슨 뜻인지 한 문장과 함께), Windows에 물을 수 없었을 때는 **확인하지 않음**입니다. 폴더의 접근
목록을 읽기만 하고 아무것도 바꾸지 않습니다. 설치 프로그램이 두는 곳, 곧 사용자 폴더의 `.codex-auto-resume`에
있으면 내 계정만의 것이고, 그 문장도 거기에 설치하라고 말합니다. 다른 곳의 폴더는 사용자 폴더 안이라도 그렇지
않을 수 있습니다. 한 예로 Codex의 Windows 샌드박스가 설정된 PC에서는 그 샌드박스 계정이 `AppData` 아래 폴더를 열
수 있고, 이 계정들도 이 PC의 다른 계정입니다.

**어떻게 되는지 보기**는 만들어 낸 문장으로 복구 하나를 보여 주며, 아무것도 보내지 않습니다. 만들어 낸 작업
하나(ID가 모두 0인 예시 대화)가 대기 중에서 1분 동안 카운트다운하며 기다린 뒤 기록에 복구됨으로 나타나고, 1분
뒤 사라집니다. 워처가 실행 중이면 그 아이콘도 중단 때 뜨는 카드를 데모라는 제목으로 보여 주며, 그 단추는
아무 일도 하지 않습니다. 이 모든 것은 복구 상태에서 읽거나 거기에 쓰지 않고, 만들어 낸 행에는 아무 동작도
없으며, 카드는 Windows 알림이 아니어서 Windows 알림 센터에 아무것도 남지 않습니다. 워처의 아이콘은 이 요청을
자기만의 Windows 이벤트로 듣는데, 그 이벤트로는 이 카드 말고 아무것도 요청할 수 없습니다.

그 뒤의 **다른 버전 설치...**는 두 판의 릴리스나 사전 릴리스를 지금 버전 대신 설치합니다. 무엇을 묻고 무엇을
바꾸는지는 [다른 버전 설치](#다른-버전-설치)에 있습니다.

맨 끝의 **실패가 이어지지 않은 이유 확인...**은 실패한 턴이 왜 이어지지 않았는지 워처 자신의 규칙에 물어, 그 답을
복사 단추와 함께 보여 줍니다. 가장 가능성 높은 이유가 쉬운 말로 맨 위에 옵니다. 이어서 최근 72시간의 대화마다
마지막 턴이 어떻게 기록되었는지와 이어 가는 대상인지, 아니라면 왜인지(다른 종류의 대화, 되돌아보는 시간 범위
이전, 더 새로운 턴, 복구하지 않는 종류)를 보여 줍니다. 이어 가는 대상인 대화에는 그 밖에 막는 것(자동 복구나 그
대화의 복구가 꺼짐, 설정에서 그 종류가 꺼짐, 이미 있는 기록, 실행 중이 아닌 워처)을 덧붙입니다. 그리고 Codex가
턴을 다른 ID로 기록하는 대화(워처가 그쪽을 따라 읽습니다), Codex 홈마다 데이터베이스를 마지막으로 쓴 때, 앱이
아는 클라우드 작업의 수(OpenAI 서버에서 실행되어 아직 이어 갈 수 없습니다), 마지막 사용량 확인, 알림이 어떻게
전해지는지, Codex 버전과 호환성, 그리고 워처가 로그에 남긴 최근 이유를 보여 줍니다. 로그는 실패한 턴을 이어 가지
않은 이유를 턴마다 한 번 씁니다. 읽기만 하며, 대화의 내용은 하나도 읽지 않고, 대화는 그 답 안에서만 통하는
별칭으로 나옵니다. 진단 정보 내보내기...에도 같은 확인이 들어갑니다.

### 관리자가 정하는 설정

v0.6.11부터 관리자는 `Software\Policies\CodexAutoResume` 아래에 일곱 가지 값을 둘 수 있습니다. PC를
쓰는 모든 사람에게는 `HKEY_LOCAL_MACHINE`에, 한 사람에게는 `HKEY_CURRENT_USER`에 둡니다. 이 제품은 그 값을
읽기만 하고 쓰지 않으며, 각 값은 복구를 붙잡아 둘 수만 있습니다. 아무도 관리하지 않는 PC에는 이런 값이
없고, 그때는 달라지는 것이 없습니다.

| 값 | 형식 | 하는 일 |
| --- | --- | --- |
| `DisableAutoResume` | DWORD, 0이 아님 | 복구가 일시 정지되고, 값이 있는 동안 자동 복구 다시 켜기는 거절됩니다. |
| `ForceObserveOnly` | DWORD, 0이 아님 | 지켜보기만이 켜집니다. 모든 확인은 하고 아무것도 보내지 않습니다. |
| `DisableUpdateCheck` | DWORD, 0이 아님 | 대시보드의 **업데이트 확인**과 **다른 버전 설치...**가 흐리게 표시되고 아무것도 묻지 않습니다. |
| `DisableStatusFile` | DWORD, 0이 아님 | **다른 도구용 상태 파일 쓰기**를 끈 채로 두며, 워처는 썼던 파일을 지웁니다. |
| `MaxRecoveryAttempts` | DWORD, 1~20 | 중단당 시도 횟수의 최댓값으로, 그 설정의 상한입니다. |
| `DisablePowerAction` | DWORD, 0이 아님 | 사용량 한도 복구 뒤의 전원 동작이 꺼지고 켤 수 없습니다. 그 전에 켜 둔 것은 남지만 아무것도 하지 않습니다(v0.6.12부터). |
| `QuietHours` | 문자열 | 다른 무엇을 정했든 적용되는 조용한 시간입니다. `22:00-07:00`처럼, 또는 시작하는 요일을 붙여 `22:00-07:00 weekdays`(또는 `weekends`, `every_day`)처럼 씁니다. 시각은 정각이나 30분이어야 합니다. |

두 곳을 모두 읽고, 어느 한쪽이 거는 제한은 모두 적용됩니다. 어느 한쪽에라도 켜진 스위치는 켜진 것이고, 더
낮은 상한이 상한이며, 어느 쪽에 둔 조용한 시간이든 사용자가 직접 정한 조용한 시간과 함께 적용됩니다. 형식이
틀렸거나, 범위를 벗어났거나, 모양이 맞지 않는 값은 없는 것처럼 무시합니다. 값은 있는데 읽을 수 없으면 - 그
값이나 키 전체에 접근이 거부된 경우처럼 - 없는 값으로 여기지 않고, 그 값이 걸 수 있었던 가장 큰 제한을 겁니다.
스위치는 켜진 것으로, 상한은 1로 보고, 시각을 읽을 수 없는 조용한 시간은 `ForceObserveOnly`처럼 어느 시각에도
아무것도 보내지 않게 합니다. 워처는 확인할 때마다, 대시보드와 패널은 설정을 읽을 때마다 이 값을 읽습니다.
`DisablePowerAction`을 뺀 위의 값 가운데 하나라도 어느 한쪽에 있는 동안 **다른 버전 설치...**는 이 값을 처음 읽는 v0.6.11-beta보다
이전 버전을 제공하지 않습니다. 그보다 오래된 버전은 이 값을 지키지 않게 되기 때문입니다.

값이 정하는 설정은 대시보드의 설정과 Codex 안의 패널에서 흐리게 표시되고, 그 아래에 **관리자가 정한
설정입니다.**라고 적힙니다. 개요는 자동 복구 옆에 **일부 설정은 관리자가 관리**라고 하거나 **관리자가
일시 정지함**이라고 하고, 진단은 적용 중인 값의 이름을 보여 줍니다. 값이 정하는 설정을 바꾸려 하면 거절되지만,
상한 안에서 시도 횟수를 정하는 것은 예외입니다. 사용자가 직접 고른 설정은 설정 파일에 그대로 남습니다. 값이 붙잡아 두는
것은 그 파일에 쓰지 않으며, 값이 없어지면 사용자 설정이 다시 적용됩니다. 일시 정지만은 예외라서,
`DisableAutoResume`을 없애도 복구가 저절로 다시 시작되지 않습니다. 업그레이드 뒤와 마찬가지로 다시 시작은
사용자가 합니다.

이 값들은 이 제품이 따르는 약속이지 잠금 장치가 아닙니다. 제품은 한 사람을 위해 그 사람의 폴더에 설치되므로,
프로그램 파일을 바꿀 수 있는 사람은 제품이 하는 일도 바꿀 수 있습니다. 소스 체크아웃에서 실행한 사본은 이
값을 전혀 읽지 않습니다. `DisableUpdateCheck`는 대시보드의 확인과 버전 목록을 끌 뿐, 사용자가 직접 실행하는
`bootstrap.ps1`까지 막지는 않습니다.

### 여러 Codex 홈

v0.6.16부터(처음에는 v0.6.15-beta로 공개되었습니다) 워처 하나가 처음 찾은 홈(`CODEX_HOME` 또는 `%USERPROFILE%\.codex`) 말고도 Codex 홈을 최대 세 개 더
맡아 복구할 수 있습니다. *설정 > 고급 > Codex 홈*에 목록이 있습니다. 폴더 - 안에 `state_<N>.sqlite`가 있는 Codex 홈 - 를
더하고 짧은 별칭을 붙이세요. 네트워크(UNC) 경로, 링크, 상태 데이터베이스가 없는 폴더, 이미 다른 이름으로 목록에 있는 같은
폴더는 거절됩니다. 홈마다 따로 읽기, `CODEX_HOME`을 그 홈으로 둔 Codex 프로세스, 잠금, 엔진으로 복구하며, 기록은 자기 홈으로만
갑니다. 대기 중, 기록, Codex 패널, 카드는 추가 홈의 기록 옆에 별칭을 보여 줍니다.

- **경로와 폴더로 잠급니다.** 각 홈은 경로와 폴더 자체 두 가지로 잠그므로, 두 설치가 한 폴더를 - 이름을 다르게 써도 - 함께
  지켜보는 일은 없습니다.
- **대시보드만 바꿉니다.** Codex의 `update_settings`는 이 항목을 거절하며 Codex로 가는 어떤 응답에도 경로가 실리지 않습니다.
  *기본값 복원*은 이 항목을 유지합니다.
- **홈 빼기.** 뺀 홈에서 기다리던 복구는 취소됩니다. 이미 그곳 Codex 대기열에 들어간 것은 끝날 때까지 지켜보며, 그 뒤에야 홈을
  놓습니다.
- **고급판은 기본 홈에서만 움직입니다.** 모든 고급 기능은 기본 홈의 기록만 봅니다. 추가 홈은 표준판처럼 복구합니다.
- **0.162까지 측정했습니다.** 데스크톱 앱이 두 번째 홈에 닿는지(측정 MH)는 `codex-cli 0.158`에서 통과했고 `codex-cli 0.162`에서
  다시 통과했습니다. 0.162보다 새로운 Codex에서는 다시 측정될 때까지 측정되지 않았다고 카드에 표시합니다.
- **찾은 홈은 제안만 하고 스스로 더하지 않습니다.** 이 PC의 Codex가 아직 감시하지 않는 Codex 홈을 쓰고 있으면 카드에
  *Codex가 <폴더>도 사용합니다. 이 홈도 감시할까요?*라고 표시합니다. 보는 곳은 두 군데뿐입니다. Windows 계정의 `CODEX_HOME`
  변수와, Codex 앱이 실행된 위치를 적어 둔 Codex 앱 자체의 목록(`%LOCALAPPDATA%\OpenAI\Codex\chrome-native-hosts-v2.json`)입니다.
  더할 수 있는 폴더만 제안합니다. 상태 데이터베이스가 있는 로컬 Codex 홈이어야 하고, 이름을 어떻게 쓰든 기본 홈이나 이미 목록에
  있는 홈이 아니어야 합니다. **추가**는 *Codex 홈 추가...*와 똑같이, 같은 세 개 제한으로 더합니다. 이미 세 개를 더했으면 그렇다고
  알려 줍니다. **나중에**를 누르면 그 폴더는 다시 제안하지 않습니다. 기본으로 켜져 있는 *이 PC에서 찾은 Codex 홈 제안* 스위치로
  찾기를 끌 수 있습니다.

### 언어

화면은 English, 한국어, 日本語, 简体中文, 繁體中文, Español, Deutsch, Français, Português (Brasil),
Русский, Italiano, Türkçe, Polski, Українська, Tiếng Việt, Bahasa Indonesia로 표시됩니다. **화면 언어**의
기본값은 *시스템*이며, Windows가 첫 번째로 꼽는 언어를 따르고(지역은 가리지 않아 포르투갈의 포르투갈어도
포함되며, 중국어는 문자 체계로 가립니다) 이 제품에 없는 언어면 영어로 표시합니다. 아랍어와 히브리어도
번역되어 있지만 아직 고를 수 없습니다. 오른쪽에서 왼쪽으로 쓰는 언어라서, 모든 화면이 좌우를 뒤집어 그릴 수
있게 된 뒤에 들어옵니다. 그때까지 Windows가 둘 중 하나로 되어 있으면 이 제품은 영어로 표시합니다. 두 언어
목록은 *시스템*(또는 *화면 언어와 같게*)을 맨 위에 두고 각 언어를 그 언어 자신의 이름으로만 보여 줍니다.
열 개쯤 보이고 나머지는 스크롤되며, 글자를 치면 그 글자로 시작하는 다음 언어로 갑니다. 직접 고른 언어는
Windows보다 우선하며 재시작·복구·업데이트 뒤에도 유지됩니다. 환경 변수 `CODEX_AUTO_RESUME_LANG`은 Windows가 알려 주는 언어를 대신하므로,
설정이 *시스템*일 때만 언어를 정합니다. 새 언어는 곧바로 보입니다. 대시보드는 그 언어로 스스로 다시
열리고, 패널은 그 언어로 다시 그려지며, 팝업, 메뉴, 알림은 다음에 나타날 때부터 그 언어를 씁니다.

### 텍스트 크기와 화면 읽기 프로그램

v0.6.11부터 대시보드, 알림 영역 팝업, 알림 카드, Codex 안의 패널은 Windows의 텍스트 크기로 글자를
그립니다. 설정 > 접근성 > **텍스트 크기**("텍스트를 더 크게")로, 읽기만 하고 바꾸지 않습니다. 대시보드, 팝업,
카드는 통째로 그만큼 크게 그립니다. 글자와 그것을 담는 모든 것을, 더 큰 디스플레이 배율이 그리듯이 그리므로
어느 것도 잘리지 않습니다. 어느 크기에서든 모든 디스플레이 배율에서와 똑같이 배치됩니다. 어느 것도 열리는
화면이 담을 수 있는 것보다 크게 그리지 않습니다. 대시보드는 가장 좁을 때와 가장 높은 대화 상자를, 팝업은
통째로, 카드는 가로세로 화면의 절반 안에서 담겨야 하며, 그렇지 않으면 담기는 가장 큰 크기로 그립니다. 패널은
글자와 한 줄을 담는 것이 함께 커지고, 나머지 줄은 줄바꿈됩니다. 대시보드는 열릴 때, 팝업과 카드는 나타날 때마다,
패널은 Codex가 열 때마다 크기를 가져옵니다.

대시보드에서 사람이 다룰 수 있는 모든 컨트롤에는 화면 읽기 프로그램이 읽는 이름이 모든 언어로 있습니다.
팝업은 스스로 그리기 때문에 Windows만으로는 그 안에 무엇이 있는지 화면 읽기 프로그램에 알려 줄 수 없었습니다.
v0.6.11부터는 내레이터와 다른 화면 읽기 프로그램에 개수, 작업마다 그 행과 스위치, 그 아래 안내,
두 버튼을 알려 줍니다. 각각의 이름, 역할, 상태, 위치와, 키보드가 움직일 때 키보드가 있는 곳까지 알려 줍니다.
화면 읽기 프로그램에서 스위치나 버튼을 누르는 것은 그려진 것을 클릭하는 것과 똑같습니다. 모든 포커스 링은
모든 디자인과 테마에서 그려진 바탕과 3:1 이상 대비됩니다.

### 이어서 하기 메시지

워처는 작업을 이어 갈 때 Codex에 짧은 메시지 하나와, 자기가 시작한 턴을 정확히 알아보기 위한 한
줄을 보냅니다. **이어서 하기 언어**는 그 메시지의 언어를(기본값은 화면 언어), **메시지 스타일**은
문장을 정합니다.

| 스타일 | 말하는 내용 |
| --- | --- |
| 간단히 | 다시 시도해 달라고만 합니다 |
| 기본(기본값) | 작업이 멈춘 이유를 말한 뒤 다시 시도해 달라고 합니다 |
| 자세히 | 지금까지의 작업을 확인하고 이미 끝난 일은 반복하지 말라고도 요청합니다 |
| 직접 입력 | 직접 쓴 문장 |

**직접 입력** 메시지는 쓴 그대로 보내며, 번역하거나 고쳐 쓰지 않습니다. 모든 중단에 쓸 메시지
하나를 쓰거나 중단 종류마다 따로 쓸 수 있고, 비어 있으면 모든 중단에 쓰는 메시지로, 그다음 기본
메시지로 대신합니다. `{reason}`, `{category}`, `{attempt}`, `{max_attempts}`, `{reset_time}`만 쓸 수
있으며, 프롬프트·답변·제목·경로·계정·토큰을 메시지에 넣게 되는 자리표시자는 이름을 밝혀 거절하고,
최대 2000자입니다. **미리보기**는 워처가 보낼 때 쓰는 바로 그 코드로 만든, 중단 종류별로 실제
보내질 문장을 보여 줍니다.

v0.6.11-beta에는 다섯 번째 스타일인 신중하게가 있었지만, 자세히가 이미 요청하는 것을 요청했기
때문에 자세히로 합쳤습니다. 신중하게를 골라 두었다면 이제 자세히가 골라져 있고, 자세히의 메시지를
보냅니다.

v0.6.11부터는 대화 하나에 그 대화만의 메시지를 둘 수 있습니다. 대시보드 대기 중 페이지의 그 작업 행에서
**이 대화에 쓸 메시지...**를 고르면 됩니다. 그 대화를 이어 갈 때마다 메시지 스타일과 상관없이 이어서 하기
메시지 대신 보내며, 그 대화에만, 복구하는 중단에만 씁니다. 그 밖에는 모두 직접 입력 메시지와 같습니다. 같은
자리표시자와 같은 2000자를 쓰고, 쓴 그대로 보내며, 대화 상자의 미리보기가 무엇을 보낼지 보여 줍니다. 채우고 나면
아무것도 남지 않는 메시지는 쓰지 않고, 그 대화에는 스타일의 메시지를 보냅니다. 최대 50개 대화까지 둘 수 있으며,
**메시지 삭제**나 기본값 복원으로 지웁니다. 설정 파일은 이를 그 대화의 ID 옆에 두고, 진단 번들에는 있다는 것만
남습니다.

#### 이번에만 덧붙일 말

v0.6.16-beta.3부터는 기다리는 작업 하나에, 그 작업의 다음 이어서 하기 메시지에만 쓸 말을 덧붙일 수 있습니다.
대시보드 대기 중 페이지의 그 작업 행에서 **이번에만 덧붙일 말 추가...**를 고르면 됩니다. 그 작업의 한도가 풀려
이어 갈 때, 원래 보낼 이어서 하기 메시지 뒤에 빈 줄 하나를 두고 한 번만 보냅니다. 무엇을 시작하거나 앞당기거나
건너뛰지 않습니다. 작업은 덧붙인 말이 없을 때와 똑같은 때에 이어지며, 모든 확인이 그대로 적용됩니다. 그 말을 담은
이어서 하기 메시지를 Codex에 넘기면, 그 뒤에 어떻게 되든 지웁니다. Codex의 대기열 프로세스가 아예 시작하지 않았을
때만 다음 시도를 위해 남겨 둡니다. 보내지 않고 작업이 끝날 때도 지웁니다. 다른 방법으로 복구되었거나, 취소되었거나,
만료되었거나, 다른 것으로 대체되었을 때입니다. 그 작업 하나에만 가고, 같은 대화의 다른 작업에는 가지 않으며, 두 번
가지도 않습니다. 그 밖에는 모두 직접 입력 메시지와 같습니다. 같은 자리표시자와 같은 2000자를 쓰고, 쓴 그대로
보내며, 대화 상자의 미리보기가 그 말을 덧붙인 다음 이어서 하기 메시지를 보여 줍니다. 그 작업의 *기다리는 이유*
설명에 덧붙인 말이 있다고 나오며, 같은 메뉴의 **이번에만 덧붙일 말 바꾸기...**와 **이번에만 덧붙일 말 지우기**로
바꾸거나 지웁니다. 설정이 아니라 상태 옆의 `config/once-words.json`에 두며, 진단 번들에는 몇 개인지만 남습니다.

직접 입력 문장은 대시보드에서만 쓸 수 있습니다. Codex는 메시지를 미리 보고 언어나 스타일을 바꿀
수 있지만, 문장 자체는 정할 수 없습니다. 직접 입력 메시지도, 대화만의 메시지도, 이번에만 덧붙일 말도 마찬가지입니다. 대화에
자동으로 보내지는 문장이 모델이 설득당해 바꿀 수 있는 것이어서는 안 되기 때문입니다.

메시지는 무엇을 복구할지를 바꾸지 않습니다. 스타일과 문장은 워처가 이미 하기로 결정한 복구에
쓸 말을 고를 뿐입니다.

## Windows 자동 시작

선택 사항이고, 사용자 단위이며, 꼭 필요하지 않습니다.

```bash
python src/auto_resume.py install --startup
```

`HKCU\Software\Microsoft\Windows\CurrentVersion\Run` 아래에 값 하나만 씁니다. 관리자 권한이 필요
없고, 시스템 전역의 것은 아무것도 건드리지 않으며, 서비스나 예약 작업을 만들지 않습니다. 콘솔 창이
뜨지 않도록 `pythonw.exe`로 워처를 실행하고, 실제로 적용 중인 홈 디렉터리를 언제나 함께 고정해
두므로 자동 시작된 워처도 같은 상태와 같은 단일 인스턴스 잠금을 씁니다.

`install --startup`을 여러 번 실행해도 항목이 중복되지 않습니다.

처음에는 한동안 포그라운드로 돌려 보고, 실제로 재개되는 것을 본 뒤에 자동 시작을 켜는 것을 권합니다.

## 제거

Windows **설정 > 앱**에서 제거하거나, 설치 마법사를 다시 실행해 **제거**를 고르거나, 릴리스 압축 파일의
`Uninstall.cmd`를 실행하거나, Codex에게 auto resume 제거를 요청하면 됩니다.
`Uninstall.cmd`는 기본적으로 설정과 대기 중인 재개를 남겨 두므로(기본 로그와 오류 로그는 지우고,
`logs\launcher.log`와 `logs\codex-start.log`는 남습니다) 다시 설치해도 잃지 않습니다.
이것까지 지우려면 `Uninstall.cmd -Purge`를 실행하거나 설치 폴더(기본값
`%USERPROFILE%\.codex-auto-resume\`)를 직접 지우면 됩니다. Codex에게 요청하면 워처를 멈추고,
Windows 등록과 플러그인을 제거하며, 함께 지워 달라고 하지 않는 한 설정과 대기 중인 재개는 남겨
둡니다. 프로그램 파일이 남아 있는 설치 폴더는 사용자가 직접 지우도록 남겨 둡니다.
`Uninstall.cmd`는 이 제품의 마켓플레이스가 아직 이 설치본을 가리키고 있으면 그것도 Codex에서
제거합니다. v0.6.16부터는 `Uninstall.cmd`와 설정의 앱 목록, `winget uninstall`(질문 없이 하려면 `-Silent`)이
이 설치본의 설정 > 앱 항목과 보관해 둔 제거 프로그램도 지웁니다. 둘 다 그것이 이 설치본을 가리킬 때만
지우며, 같은 이름이어도 다른 설치본을 가리키는 항목은 그대로 둡니다.

소스 체크아웃에서는 같은 명령줄 도구가 이 도구의 상태와 로그까지 지웁니다(`--keep-logs`를 붙이면
로그가, `--keep-state`를 붙이면 설정과 대기 중인 복구가 남습니다).

```bash
python src/auto_resume.py uninstall
```

```bash
python src/auto_resume.py uninstall --keep-logs
```

제거는 의도적으로 보수적입니다.

- 먼저 워처에 멈춰 달라고 요청합니다. 그 뒤에도 워처가 실행 중이거나 **실행 여부를 확인할 수
  없으면** 아무것도 지우지 않고 중단합니다.
- v0.6.16부터 `Uninstall.cmd`, 설정의 앱 목록, 설치 마법사의 제거는 업데이트처럼 열린 대시보드에 먼저 닫아
  달라고 요청하고, 무엇이든 지우기 전에 이 설치본의 무엇도 파일을 붙잡고 있지 않은지 확인합니다. 저장하지 않은 설정
  변경이 있는 대시보드, 닫히지 않는 대시보드, 설치본에서 아직 실행 중인 프로그램이 있으면 아무것도 지우지 않고
  멈추며 무엇을 닫아야 하는지 알려 줍니다.
- 로그인 자동 시작 값, 알림 식별자, 설정 > 앱의 항목은 **이** 설치본에 속할 때만 제거합니다. 다른 사본을 시작하는
  값은 지우지 않고 알립니다. 시작 메뉴 항목은 알림 식별자가 다른 설치본에 속해 있으면 남겨 둡니다.
  알림 식별자가 아예 등록되어 있지 않으면, 정해진 위치에 있는 시작 메뉴 항목을 누구의 것인지
  확인하지 않고 제거합니다.
- 자기 것임을 증명할 수 있는 디렉터리 안에서만 지웁니다. 소스 명령은 지우려는 디렉터리마다 이
  도구의 소유 표시 파일(`.owned-by-codex-auto-resume`)가 있어야 하고, `Uninstall.cmd`는 설치
  루트나 `config/`에 그 마커가 있거나 `runtime.json`이 바로 그 디렉터리를 가리켜야 합니다. 단지
  `app`, `runtime`, `config`, `logs`라는 이름의 폴더가 들어 있을 뿐인 디렉터리는 거부하고 그 사실을
  알리며, 그 안의 것은 하나도 지우지 않습니다.
- 소스 명령은 소유한 디렉터리 안에서도 자기 파일 이름만 지우므로 그 안의 관계없는 파일은
  남습니다. `Uninstall.cmd`는 프로그램 폴더 `app\`과 `runtime\`을 통째로 지우고, `-Purge`를 붙이면
  `config\`와 `logs\`의 나머지도 지웁니다.
- `Uninstall.cmd`는 이 플러그인과 마켓플레이스가 아직 이 설치본을 가리키고 있을 때에만 `codex`
  CLI에 제거를 요청하고, 다른 곳을 가리키고 있으면 그대로 두고 알립니다. 플러그인을 제거하면
  Codex가 자기 캐시에 있던 플러그인 사본을 지웁니다. 소스 명령은 Codex 등록을 건드리지 않습니다.
- 어느 방법도 ChatGPT나 Codex 대화, Codex 파일, 사용자 저장소, 상위 디렉터리를 직접 지우지
  않습니다.

## 안전 모델

실행 중에 이 도구가 직접 쓰는 것은 자기 `config/`와 `logs/`(그리고 Python이 이 도구의 프로그램 폴더 안에 쓰는 바이트코드 캐시)입니다. 설정에서
로그인 시 자동 시작을 켜거나 끄면 사용자 단위 Run 값이 바뀌고, 표시한 알림은 Windows 알림 기록에 남습니다. 자기 폴더 바깥에 쓰는 것은 하나뿐이고, 요청했을
때만 씁니다. 진단 페이지의 **진단 정보 내보내기...**와 명령줄의 `diagnostics`는 ID를 별칭으로 바꾸고 경로, Windows 사용자 이름, 이메일 주소처럼 생긴 문자열을 지운 JSON 묶음
하나를 사용자가 고른 경로에 씁니다. 아무것도 전송하지 않으며, 이미 있는 파일은 덮어쓰지 않습니다. 공식 인터페이스로 Codex에 요청하는 것은 정확한 스레드 하나에 이어서 하기
메시지 한 건을 넣는 것(`codex queue`)과, 필요하면 그 메시지를 거둬들이는 것(App Server의 `thread/queue/delete`)입니다. 설치할
때는 `codex` CLI에 이 플러그인과 로컬 마켓플레이스 등록을 요청하며, 이 제품의 이름(`codex-auto-resume-windows`)으로 이미 등록된
마켓플레이스가 있으면 이 설치본을 가리키도록 바꿉니다. 또 설치할 때는 마켓플레이스를 새로 고치라고 Codex에 요청합니다. v0.5.7의 설치 프로그램은 사용자가 설정해
둔 모든 Git 마켓플레이스를 새로 고칩니다. `codex-auto-resume-windows`만 새로 고치는 동작은 v0.6.0부터입니다. `Uninstall.cmd`는
이 플러그인과 마켓플레이스가 아직 이 설치본을 가리킬 때에만 `codex` CLI에 등록 해제를 요청합니다. v0.6.16부터 설치는 설정 > 앱의
항목도 씁니다. `HKCU\Software\Microsoft\Windows\CurrentVersion\Uninstall` 아래의 사용자 단위 키 하나로 `CodexAutoResume`이며, 다른
판은 거기에 판 이름이 붙습니다. 또 그 항목이 가리킬 수 있도록 설치 프로그램 자신의 제거 사본을 설치본 안(`uninstall\install.ps1`)에 보관합니다.
제거는 그 항목이 이 설치본을 가리킬 때에만 지웁니다.

코드로 강제하는 설계 규칙:

- **네트워크 코드 없음.** 복구 런타임은 네트워크 모듈을 import하지 않으며, `src/`나 `scripts/`
  아래에서 git이 추적하는 Python 파일에 `socket`, `ssl`, `http`, `urllib.request` 같은 흔한
  네트워킹 모듈을 import하는 줄이 생기면 테스트가 실패합니다. 그래서 워처는 스스로 연결을 열지
  않습니다.
  무엇이 무엇을 거쳐 네트워크에 닿는지는 [개인정보](#개인정보)에 있습니다.
- **Codex 파일을 쓰기 모드로 열지 않음.** Codex 데이터베이스는 `mode=ro`와 `query_only`로 열며,
  Codex의 데이터베이스, rollout, 설정 파일 중 어느 것도 쓰기 모드로 열지 않습니다. SQLite의 WAL
  모드 데이터베이스라면 읽기 전용 연결도 그 옆의 공유 메모리 인덱스(`-shm`)를 갱신할 수 있으며,
  Codex의 데이터베이스가 WAL을 쓰는지는 확인하지 않았습니다. Codex의 상태를 바꿀 때는 위에 적은
  대로 Codex에 요청합니다. 이 도구가 실행하는 Codex 프로세스는 여느 Codex 프로세스처럼 Codex 자신의
  로그와 캐시를 갱신할 수 있습니다.
- **실패하면 닫힘(fail closed).** 로드 상태를 모르거나, 사용량을 모르거나, 확인 수단을 쓸 수
  없거나, 조금이라도 모호하면 보내지 않고 기다립니다.
- **마지막 순간에 다시 확인.** 보내기 직전에 기록을 다시 읽어, 그 기록이 여전히 유효하고 허용되어
  있는지, 같은 앱이 실행 중이고 스레드가 로드되어 있는지, 사용량이 남아 있는지(읽은 지 30초가
  넘지 않은 사용량 값으로)를 확인합니다. 예약은 SQLite 쓰기 트랜잭션 하나로 이루어지므로 한 중단을
  예약할 수 있는 워처는 하나뿐이고, 하나의 Windows 세션 안에서는 같은 상태 디렉터리에 대해 한 번에
  워처 하나만 실행될 수 있습니다.
- **정확히 그 스레드만.** 스레드 ID는 정규 UUID인지 검증하고 별도의 argv 요소로 넘깁니다. Python
  코드는 `shell=True`, `os.system`, `eval`, `exec`를 쓰지 않고, 모든 하위 프로세스를 인자 목록으로
  실행합니다.
- **분류할 수 있는 것만.** 분류하지 못한 장애는 재시도하지 않으며,
  [무엇을 복구하고 무엇을 복구하지 않는가](#무엇을-복구하고-무엇을-복구하지-않는가)에서 복구하지
  않는다고 적은 종류도 재시도하지 않습니다.
- **값은 데이터일 뿐 스크립트가 아님.** Windows PowerShell은 설치 프로그램, 제거 프로그램, 플러그인 설치
  스크립트를 실행하며, 이 도구의 코드도 프로세스 목록 조회, 알림 표시, 시작 메뉴 바로 가기 생성에
  매번 고정된 스크립트로 PowerShell을 씁니다. 대화 제목이나 폴더 이름 같은 값은 환경 변수로 넘기며,
  스크립트는 이를 평범한 텍스트로 읽을 뿐 실행하지 않습니다. v0.4.0부터 v0.5.6까지의 릴리스는 그런
  이름을 스크립트 본문에 넣었기 때문에 곡선 따옴표가 든 이름이 PowerShell 코드를 실행할 수 있었고,
  v0.5.7부터는 값을 데이터로만 넘깁니다.
- **중복 재개 없음.** 외부 프로세스가 메시지를 받을 수 있게 되기 전에 중단 기록을 영속적으로
  예약합니다. 전송 결과가 불확실하면 다시 보내지 않습니다. 워처는 그 메시지가 실제로 도착했는지
  최대 24시간 동안 계속 확인하고, 도착했다면 재개된 것으로 기록합니다.
- **로그는 내용이 아니라 코드로.** 엔진 이벤트는 고정된 메시지 표에서 사유 코드, 타임스탬프,
  식별자로 기록하고 그 밖의 세부 값은 가리므로, 이 경로로는 프롬프트 내용, Codex 오류 본문, 계정
  식별자가 기록되지 않습니다. 기본 로그에는 이 도구의 상태 디렉터리 경로도 기록되는데, 기본
  위치라면 이 경로에 Windows 사용자 이름이 들어 있습니다. 엔진의 버전 문자열도 기록되는데, v0.6.4까지는
  검증되지 않은 엔진일 때만이었고, v0.6.5부터는 어느 엔진이든 호환성 레지스트리의 코드와
  함께입니다. Traceback은 별도의 순환 로그 `errors.log`에 기록되며, 여기에도 로컬 경로가 들어
  있습니다. 런처는 자기 예외 메시지를 `logs\launcher.log`에 기록합니다.
- **설정은 정책일 뿐.** 어떤 설정도 안전 속성을 끌 수 없습니다. [설정](#설정)을 참고하세요.
- **쓰지 않는 것:** GUI 자동화, 마우스·키보드 시뮬레이션, OCR, 화면 스크래핑, 접근성 API 클릭,
  바이너리 패치, DLL 주입, 프로세스 메모리 조작, 자격 증명 추출. v0.6.11부터 팝업은 자기 창에 대한
  화면 읽기 프로그램의 질문에 답합니다(텍스트 크기와 화면 읽기 프로그램). 다른 어떤 창에도 아무것도 묻지
  않습니다.

## 개인정보

이 프로젝트로 전송되는 것은 없습니다. 텔레메트리, 분석, 크래시 리포트, 자동 업데이트 확인, 자동 호환성
데이터 새로 받기가 없으며, 그것을 받을 이 프로젝트의 서버도 없습니다. 이 도구 자체는 프롬프트, 어시스턴트 응답, 도구 입출력,
파일 내용, 계정 식별자, 자격 증명, 오류 본문 중 어느 것도 어디로도 전송하지 않습니다. 복구
런타임(`src/`, `scripts/*.py`)은 네트워크 모듈을 import하지 않으며, `src/`나 `scripts/` 아래에서
git이 추적하는 Python 파일에 `socket`, `ssl`, `http`, `urllib.request` 같은 흔한 네트워킹 모듈을
import하는 줄이 생기면 테스트가 실패합니다.

이 도구 때문에 네트워크에 닿는 것은, 지금까지 확인한 범위에서는, OpenAI와 GitHub, 그리고 v0.5.7의 설치 프로그램이 실행되는 동안에는 사용자의 다른 Git 마켓플레이스가 호스팅된 곳으로 갑니다.

- **OpenAI, Codex를 통해서.** 재개하기 전에 이 도구가 실행한 공식 Codex 프로세스가 현재
  사용량을 OpenAI에 묻습니다. 재개된 턴은 데스크톱 앱 안에서 사용자의 Codex 설정대로 실행되며,
  직접 시작한 턴과 똑같이 그 대화를 OpenAI로 보냅니다. Codex 대화 안에서 이 플러그인의 도구나
  명령을 실행하면 그 결과(상태, 대화 ID가 담긴 대기 목록, 그리고 `status`, `doctor`, `logs` 같은
  명령이 출력하는 로컬 경로. 기본 위치라면 이 경로에 Windows 사용자 이름이 들어 있습니다)도 그
  대화의 일부가 되어, 여느 도구 출력처럼 Codex가 OpenAI로 보냅니다. v0.5.7에서는
  `get_status`와 `open_settings` 도구도 설치 폴더 경로를 돌려줍니다. 이 두 도구에서 경로를 빼는
  변경은 v0.6.0부터입니다. 명령은 여전히 로컬 경로를 출력합니다.
- **GitHub, 설치할 때.** 플러그인으로 설치하거나 업데이트하면 설치 스크립트가 GitHub에서 해당
  버전의 릴리스 압축 파일을 HTTPS로 내려받습니다(그 버전의 다이제스트가 플러그인에 기록되어 있지 않을
  때는 `.sha256` 파일도 함께). 올려 보내는 것은 없지만, 여느 다운로드와 마찬가지로 GitHub는 그
  요청을 보게 됩니다. 압축 파일을 직접 내려받는 것도 같은 GitHub 다운로드이며, 그 뒤
  `Install.cmd`는 스스로 아무것도 내려받지 않지만 마켓플레이스 새로 고침은 Codex에 요청합니다(다음
  항목).
- **GitHub, 사용자가 요청할 때.** 진단 페이지의 *업데이트 확인*은 페이지를 읽지 않는 `HEAD` 요청 한 번으로
  github.com에 가장 최근 릴리스를 묻습니다. v0.6.11부터는 이어서 이 PC에 관한 것을 아무것도 싣지 않은
  `GET` 한 번으로 api.github.com에서 이 저장소의 최신 릴리스 열 개 목록을 읽어 더 새로운 사전 릴리스를
  찾으며, 찾은 것은 제안만 합니다. 같은 페이지의 *다른 버전 설치...*도 그 목록을 전부 읽습니다. 누를 때와
  버전을 확인할 때, api.github.com의 주소 하나에 한 번에 릴리스 30개씩 최대 다섯 번 `GET`을 보내며, 그다음
  확인한 압축 파일만, 고정된 다이제스트가 없으면 그 `.sha256`도 함께 내려받습니다. 관리자의 정책이 있는지는
  이 PC의 레지스트리에서 읽을 뿐 어디에도 보내지 않습니다. v0.6.5부터는 같은 페이지의 *호환성 데이터 새로
  받기*와, github.com이 답한 *업데이트 확인*이 raw.githubusercontent.com의 고정된 주소 하나로 `GET`을 한 번
  보내 Codex 호환성 데이터를 받아 옵니다. 요청에는 사용자의 기계에 관한 것이 들어 있지 않습니다. 이
  설치본 자신의 검증기가 올바른 데이터일 때만 보관하며, 그 데이터는 워처를 더 조심스럽게 만들 수만
  있습니다. 어느 것도 사용자가 요청하지 않으면 일어나지 않습니다. 다른 사람들이 어떤 Codex 버전에 대해 보고한
  것은 아예 받아 오지 않습니다. 그 횟수는 릴리스와 함께 오며, 사용자의 보고서는 따로 있는 보고 도구로 사용자가 직접
  풀 리퀘스트를 열 때만 GitHub에 갑니다.
- **설치 프로그램이 실행될 때의 마켓플레이스 호스트.** v0.6.0은 `codex-auto-resume-windows`만 지정합니다.
  로컬 등록으로 바꾼 뒤에도 예전 Git 등록이 남아 있으면 Codex는 그 등록이 가리키는 곳에서 가져옵니다.
  v0.5.7까지의 설치 프로그램은 모든 Git 마켓플레이스를 새로 고치도록 요청하며, 그 호스트는 OpenAI나
  GitHub가 아닐 수도 있습니다.
  [릴리스 압축 파일로 설치](#릴리스-압축-파일로-설치)를 참고하세요.

Codex의 로컬 상태는 읽기 전용으로 엽니다. 복구 판단은 Codex의 구조화된 기록(그리고 Codex가 오류
코드를 기록하지 않은 경우에만 오류 메시지 속 전송 장애 문구의 짧은 목록)으로 하고 대화 내용으로
하지 않지만, 대화 내용을 지나가는 읽기는 있습니다. 사용량 한도의 재설정 시각을 찾으려고 실패 직전의
rollout 파일을 최대 8 MiB까지 메모리에서 파싱해 사용량 한도 숫자만 남기고, 자기 메시지가
도착했는지 확인하려고 SQLite가 그 대화의 사용자 메시지와 대기 메시지에서 자기 표식을 찾게 합니다.
그 내용은 메모리에서만 다루고 버리며, 저장하지 않고 기본 로그에도 남기지 않습니다.

이 도구가 자기 기록으로 남기는 것은 설치 폴더(기본값 `%USERPROFILE%\.codex-auto-resume\`) 아래에
있습니다. 그 밖에는 시작 메뉴 바로가기, 로그인 항목, 알림에 필요한 Windows 등록, 그리고
Codex에 등록된 이 플러그인과 마켓플레이스를 남기며, 이 중 이 설치본에 속한 것은 `Uninstall.cmd`가
정리합니다. 이와 별개로 Windows 알림 기록에는 표시했던 알림이 남고, 재개된 대화에는 이어서 하기
메시지와 그 표식이 대화의 일부로 남습니다.

직접 입력 메시지는 설치 폴더 안의 로컬 설정 파일에만 저장됩니다. 다만 다른 모든 이어서 하기 메시지와
마찬가지로, 그 문장은 재개된 대화에 보내져 대화의 일부가 되고 그 대화와 함께 OpenAI로 갑니다. 그러니
대화에 넣고 싶지 않은 내용은 쓰지 마세요. 화면 번역은 제품과 함께 설치되는 로컬 파일이며, 언어를
고르거나 바꾸는 일로 네트워크 요청이 생기지는 않습니다. 자세한 내용은
[PRIVACY.ko.md](PRIVACY.ko.md)를
참고하세요.

## 알려진 제한

- 앱에 이미 로드된 스레드만 자동 재개할 수 있습니다. 로드되지 않은 스레드는 사용자가 열 때까지 기다립니다.
- Windows 전용입니다. Windows 10/11의 Windows ChatGPT/Codex 데스크톱 앱과 함께 동작합니다.
- 사용량을 막은 버킷이 어느 것인지 언제나 확실히 가려낼 수는 없습니다. 그래서 기록을 믿지 않고,
  보내기 직전에 지금 사용량이 남아 있는지 실시간으로 다시 확인합니다.
- Codex 앱 업데이트는 대개 견디지만 보장하지는 않습니다. 데이터베이스 파일은 스키마 세대(`state_5` ->
  `state_6`)로 찾고 실제로 읽는 열로 검증하며, 업데이트된 엔진은 `codex queue` 인터페이스가 그대로면
  받아들입니다. 이 도구가 읽는 열을 없애거나 queue 인터페이스를 바꾸는 변화는 여전히 이 도구를
  멈춥니다. 잘못 추측하는 대신 거부합니다.
- 예약한 뒤 전송 결과를 알기 전의 좁은 구간에서 워처 프로세스가 죽으면, 중복을 무릅쓰는 대신 그
  중단은 일부러 재개하지 않은 채 남깁니다.
- 전체 경로는 이제 일상적인 사용에서 한 번 관찰되었습니다. 실제 사용량 한도가 감지되었고, 스레드가
  로드되어 있음이 확인되었고, 중단이 예약되었고, `codex queue`로 이어서 하기 메시지 한 건이
  제출되었고, 30초 뒤 전달이 따로 확인되었습니다. 한 번의 실행일 뿐 쌓인 실적은 아닙니다. 일시적
  장애의 복구는 테스트로만 확인했고, 실제 장애로는 아직 겪어 보지 않았습니다.
- 알림 영역 팝업은 탐색기에서 실제로 아이콘을 클릭해 여는 방식으로는 아직 확인하지 않았습니다.
- 어떤 번역도 원어민의 검토를 거치지 않았습니다. 테스트는 각 번역이 빠짐없는지, 자리표시자를 지키는지,
  최신인지를 확인하며 문구는 확인하지 않습니다.

## 테스트

자동 테스트 실행:

```powershell
$env:PYTHONPATH = 'src'
python -m unittest discover -s tests
```

이 테스트들은 가짜 객체와 임시 디렉터리를 씁니다. ChatGPT 앱에 접속하지 않고 어떤 대화에도 메시지를
보내지 않으므로 어디서든 안전하게 실행할 수 있으며, CI가 돌리는 것도 이 테스트입니다. CI는 이 테스트를
모두 Python 3.12, 3.13, 3.14에서 반드시 통과해야 하는 작업으로 돌리고, 3.15 사전 릴리스에서는 결과를
보여 주되 막지는 않는 참고 작업으로 돌립니다.

실제 환경을 상대로 하는 점검도 있으며, 직접 켜야만 실행됩니다. 바이너리 탐색, 앱 페어링, 로드 상태
분류, 사용량 읽기를 검증합니다. 어떤 대화에도 메시지를 보내지 않지만, 사용량을 읽을 때는 워처가
재개하기 전에 하듯이 Codex를 통해 OpenAI에 현재 사용량을 묻습니다.

```powershell
$env:CODEX_AR_LIVE = '1'; $env:PYTHONPATH = 'src'; python -m unittest tests.test_integration_live
```

## 보안

전체 보안 모델, 검토 과정, 발견되어 고친 문제는 [SECURITY.ko.md](SECURITY.ko.md)에 있습니다.
요약하면, 복구 런타임에는 네트워크 코드가 없고 자격 증명을 읽지 않습니다. Codex의 상태는 읽기 전용으로 읽고, Codex의 파일은 어느 것도 쓰기 모드로 열지
않으며, Codex의 상태를 바꿀 때는 공식 인터페이스로 Codex에 요청합니다. OpenAI에 닿는 것은 Codex 자신의 통신이고, 불확실하면 보내지 않고 멈추며,
제거는 보수적입니다. 배포되는 코드가 스스로 하는 다운로드는 플러그인 설치 스크립트가 GitHub에서 해당 릴리스를 가져오는 것뿐이며, 설치하기 전에 그 파일을
확인합니다. v0.5.7의 설치 프로그램은 사용자가 설정한 Git 마켓플레이스를 새로 고치라고 Codex에 요청하기도 합니다 ([릴리스 압축 파일로
설치](#릴리스-압축-파일로-설치) 참고). v0.5.4 이후의 릴리스 압축 파일에는 GitHub 빌드 출처 증명(attestation)도 있으며, 내려받은 파일을 직접
확인하는 방법은
[docs/VERIFY.ko.md](VERIFY.ko.md)에
있습니다. v0.5.0부터 v0.5.7까지의 압축 파일은 모두 예전의 단일 작업 릴리스 워크플로가 GitHub Actions를 고정되지 않은
태그로 참조해 빌드했고, 그 실행 파일은 바이트 단위로 똑같이 다시 빌드할 수 없습니다. 빌드와 공개 작업의 분리, 커밋에 고정한 action, 재현 가능한 실행 파일은
v0.6.0부터입니다. 이 프로젝트가 빌드하는 것은 어느 것도 Authenticode 서명이 되어 있지 않고, 함께 들어 있는 Python 인터프리터는 Python
Software Foundation의 서명을 유지합니다.

이 프로젝트는 세 차례의 적대적 검토와 뮤테이션 테스트, 크래시 구간 매트릭스, 프로세스 간 경합
테스트를 거쳤습니다. 확인된 문제는 고쳤고 회귀 테스트로 덮었습니다.

보안 문제를 발견하면 이 저장소에 이슈를 열어 주세요. 공개 이슈에 자격 증명, 토큰, 비공개 대화
전문, 비공개 저장소 내용을 붙여넣지 말아 주세요. 진단에 필요하지 않습니다.
